## Update 2026-09-26 — M18.3c (GPU-built draw commands)

- **PR #192 LANDED on `main` as `c9c20e5`** (squash), all 8 CI checks green: 3-OS build & test,
  format/lint/license, ASan+UBSan, TSan (Clang), SDK consumer, editor smoke. Worktree and branches

  selection's per-group verdict, which is ADR-0043 gate 4's "no GPU readback decides the same
  frame's draw list".
- **What landed in the API:** `select_virtual_geometry_on_gpu(..., VirtualGeometryGpuSelectionBuffers*
  keep_flags)` retains the per-group flag buffer (caller owns it, must outlive the frame);
  `request.gpu_selection` + `request.max_draws` on the visibility pass;
  `VirtualGeometryDrawCandidate` (48 B), `kVirtualGeometryMaxDrawCandidates = 4096`,
  `VirtualGeometryGpuBuildCounters`; new shader `engine/render/shaders/vg_build_draws.comp`.
  The CPU keeps the gates only it can answer and uploads candidates; the builder owns exactly one
  gate, "is this cluster's group on the cut?".
- **Two decisions, both deliberate deviations worth knowing:**
  1. **One dispatch, not the two (count-then-fill) the 09-25 handoff recorded as decided.** At
     N <= 4096 each invocation scans the whole candidate array, so it knows the total AND its own
     rank; the overflow decision needs no barrier or second submit. It also makes compaction a
     deterministic **rank scan** rather than an `atomicAdd` append — an append's order varies per
     run, which would make the command buffer irreproducible and leave cross-cluster depth ties to
     scheduling. Cost O(N^2) flag reads over <=16 KB; a bigger ceiling wants a prefix sum.
  2. **Overflow degrades to the coarse cut** (coarse but hole-free), which is why a coarse-group
     cluster is accepted as a candidate despite the leaf-only rule — the overflow is not known until
     the builder has run.
- **`selected_buffer` question from the 09-25 handoff is answered:** it is no longer destroyed after
  readback when the caller asks for it. The CPU-oracle fallback path (asset deeper than the shader's
  fixed stacks) uploads the oracle's verdict into the same buffer shape, so "too deep" can never be
  read as "nothing selected" — whose safe interpretation is *draw nothing*, i.e. a vanished object.
- **Verified** (RTX 3060, validation layers ON, build run as its own command, exit 0): the same
  request through the CPU and GPU paths renders **byte-identical images**; `rime_render_tests`
  105/105 with 483,203 assertions; `ctest --preset dev` 71/71; the new case confirmed compiled in

### THE ONE BLOCKER, and it needs Luca

**A clock-pinned starbase run may be impossible.** ADR-0047 §2 ratifies the starbase bar from a
clock-pinned run. `-lgc`, `-lmc` and `-ac` all reported success on the host and the clock stayed at
**139 MHz at 0% utilisation** throughout. The likely cause is that Pascal's application clocks apply
to **CUDA** contexts while this workload is Vulkan, and locked graphics clocks are Volta-and-later.
If that holds, ADR-0047's precondition **cannot be met as written**, and the choice is Luca's:
ratify the bar from unpinned runs (and say so wherever it is quoted), or have no starbase bar and
make no hosted performance claim. `docs/perf/m18.3d-starbase/README.md` states it and takes neither
side. Until then **there is no starbase bar**.

### Two lessons worth not relearning

- **A test that only ever runs on one OS is a test about that OS.** The supervisor went red on
  Windows (ungated Unix sockets) and then twice on macOS (`/proc/<pid>`, then `/bin/false`, which is
  `/usr/bin/false` there). All three were in tests, not code.
- **Building one target is not building the tree.** #200's targeted build passed while the full build
  failed: a public header naming `stream::Codec` needs `rime::stream` linked **PUBLIC**, and a
  PRIVATE link compiles the library and breaks every consumer.

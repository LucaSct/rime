# Brick spec: hoist the world-inertia compose out of the velocity sweep

The design below is DECIDED. Build it as written. Do not redesign it, do not widen it.
**Say plainly what contradicts this spec, rather than working around it.**

## Why

`#313` measured that **94.0 %** of the worst solve step of `samples/99-the-block` is
`solve_velocities` — 4958 us of a 5273 us island, one velocity iteration costing 619.8 us.
`sim.block` p99 is 8.7 ms against a 6.000 ms budget.

Inside that sweep, one quantity is recomputed in the innermost loop and must not be.
`apply_impulse` (`engine/physics/src/solver.hpp` ~177) calls the four-argument
`apply_inv_inertia(orientation, inertia_principal, inv_inertia, r x p)` once per body per impulse
application. That overload **composes `q * inertia_principal` and then performs two quaternion
rotates, on every call.** The comment above it (`solver.hpp` ~108) says the compose is
*"DELIBERATELY not cached per tick: the NGS position pass rotates bodies mid-pass and re-reads their
orientation"*.

**That reason is true of `solve_positions` and false of `solve_velocities`.** Nothing in
`solve_velocities` writes `orientation`; the pose-integration loop that does runs *after* it, inside
`solve_island` (`engine/physics/src/world.cpp` ~1338). So across all `kVelocityIterations = 8`
iterations each body's orientation, its composite and its world inverse inertia are **constant**.
Upper bound on the waste: ~2.6e5 composes per step, for a quantity with 362 distinct unchanging
values.

## What to build — TIER 1 ONLY, and it must be BIT-IDENTICAL

The four-argument overload is literally `apply_inv_inertia(q * principal, inv_inertia_body, l)`. So
caching `q * principal` per body and calling the three-argument overload with it produces **the same
float bits**, provided the cached value is computed by the same multiply. That is the whole claim of
tier 1 and it is why `world_hash()` must not move.

1. **New per-body array.** Add a `std::vector<core::Quat>` to `PhysicsWorld::Impl` beside the other
   per-body SoA vectors, kept the same length as them (grow/swap-remove wherever the siblings do —
   find every site; `inertia_principal` is the one to mirror).
2. **Fill it once per step**, immediately before the `SolverBodies bodies{...}` construction at
   `world.cpp` ~1246: for every dense body `i`, `inertia_orientation[i] = orientation[i] * inertia_principal[i]`,
   in the same order and with the same multiply the overload uses. Sequential, on the calling thread,
   outside every parallel region. One pass over the bodies, not per island — statics are shared
   anchors between islands and a per-island fill would be a cross-island write race on them.
3. **Expose it** as `const core::Quat* inertia_orientation` on `SolverBodies`, wired from the new
   vector at the construction site.
4. **Use it in the VELOCITY PHASE ONLY** — `apply_impulse` (both bodies) and
   `prepare_contact_constraint`'s two calls. All of those run before any orientation is written in
   the step, so the cache is never stale for them.
5. **Do NOT touch `solve_positions`.** It re-reads the rotated pose mid-pass and that is the point of
   NGS; it keeps the live four-argument path.
6. **Correct the comment at `solver.hpp` ~108.** It currently says the compose is deliberately not
   cached *per tick*; it must say that it is cached for the **velocity phase**, where orientation is
   constant, and deliberately **not** used by the NGS position pass, which rotates bodies mid-pass
   and re-reads their orientation. Say why in the house teaching style, and name where the cache is
   filled. Also record that `prepare` and the sweep share it because both run before integration.

**Nothing else changes.** No iteration count, no threshold, no ordering, no 3x3 matrix (that is
tier 2, below, and it is NOT shipped in this brick).

## Proof that it is bit-identical — this is the brick's real gate

1. **Before you change anything**, on `main`'s tree, capture `world_hash()` after a fixed number of
   steps of a deterministic fixture that actually exercises rotation and friction (reuse whichever
   fixture the existing hash tests use; a stack that settles is ideal). Print it. Record it in your
   report.
2. After the change, the same fixture must produce **the same hash**. If it does not, the change is
   **not** bit-identical and that is a bug to report, not a number to re-baseline. Say so and stop.
3. **Do not commit a hardcoded golden hash as a test.** CI builds on three OSes and two compilers
   and cross-platform float identity is not a property this project claims; a pinned constant would
   be a landmine. The portable test to ADD instead, in `tests/physics/solver_test.cpp`:
   - the composed identity, bitwise: for a spread of orientations, principal rotations, inverse
     inertias and input vectors (include a non-identity `principal`, a non-unit-axis orientation and
     a zero `inv_inertia`), `apply_inv_inertia(q, principal, ii, l)` is **bitwise equal** to
     `apply_inv_inertia(q * principal, ii, l)` — compare the bits, not with a tolerance;
   - **freshness**: after `world.step(dt)`, every dense body's cached composite equals
     `orientation[i] * inertia_principal[i]` recomputed from the post-step state... **if and only if**
     that is actually true after the step. It is NOT: the fill happens before integration, so the
     cache holds the PRE-integration composite once the step returns. Work out what the correct
     invariant is, assert *that*, and say in a comment what the cache is and is not valid for. Do not
     assert something false and then loosen it.
4. The whole `ctest --preset dev` suite must pass unchanged. A test that changes result is evidence
   against bit-identity — report it rather than adjusting it.

## Two things I already know, so you do not spend the budget rediscovering them

**1. Bit-identity is a HYPOTHESIS, not a guarantee, and the likely culprit has a name.** The claim
rests on `q * principal` producing the same bits in the fill loop as it does inlined inside the
sweep. Same function, same operands — but GCC defaults to `-ffp-contract=fast`, which lets a
multiply-add fuse into an FMA, and whether it fuses can differ between two inlining contexts. So if
the hash moves, the first hypothesis is **FMA contraction, not a logic error**. Report the hash
difference, say whether the composite quaternions themselves differ bitwise from the live product
(that is the test to run next, and it localises it immediately), and stop rather than re-baselining.
A tier 1 that is not bit-identical is a different decision — the owner's, not yours.

**2. Do NOT also hoist the per-constraint velocity loads. It is a real win and it is the NEXT brick.**
`apply_impulse` reads and writes `linear_velocity[ia]`, `angular_velocity[ia]` and both of b's rows
on every impulse application — roughly six memory round-trips per contact point per iteration on the
same four rows. Within one constraint only bodies a and b are touched, so loading all four into
locals once per constraint per iteration and storing them at the end is arithmetically identical and
cuts the traffic. It is deliberately **out of scope here** so that the two gains can be attributed
separately. Do not fold it in, and do not mention it as a suggestion in your report — it is already
recorded here.

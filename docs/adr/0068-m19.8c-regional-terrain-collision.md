# ADR-0068 (m19.8c): Regional terrain collision — barrier-only activation, deferred admission, the stall as a safety net

- Status: Accepted
- Date: 2026-10-06

## Context

ADR-0067 (m19.8b) made the asset server able to give terrain memory back. This brick decides which
heightfield tiles are in the **physics world**, on the server and on a predicting client, when the
map is too large for all of them.

The hard part is not loading. It is that "is the ground there?" now has an answer that depends on a
disk, and a simulation whose outcome depends on which read finished first is one that two machines —
or two runs on one machine — cannot agree on. An outside consult (`gpt-6-astra`, read-only,
2026-10; its citations were checked against the code) proposed the shape built here, with one
difference: it recommended stalling the whole authoritative tick whenever coverage was missing.

**Owner decisions (Luca, 2026-10-05/06, recorded in the m19.8c brick spec):**

1. Terrain collision streams **regionally** on server and client — not fully resident.
2. **Defer admission from the start.** An entity whose spawn or teleport lands on terrain that is
   not installed is *held out of the simulation* and retried at each tick barrier; everyone else
   keeps ticking. Not a whole-server stall, and not island freezing.
3. M19 ends with full LOD for seamless travel (later bricks).

## Decision

### 1. A removable module, `engine/terrain_collision`

`rime::terrain_collision` depends on the public interfaces of `assets` and `physics` and on nothing
else — no renderer, no network. Nothing in `engine/` depends on it, so the engine builds without it
(guardrail 2). It is the one place that needs both the streamed asset handles and the physics
heightfield store, and neither of those may know about the other.

It keeps a sorted vector of records keyed by `TileKey{x, z, revision}`: the asset handle, the
physics shape and body ids, pins counted **by reason**, and a lifecycle state
(`Pending → Requested → Installed`, or `Failed`).

Tiles come from a `TileSource` seam: the manifest (which coordinate has terrain, at which revision)
plus request / state / resolve / release with the ADR-0067 contract. `AssetServerTileSource` is the
production implementation. The seam exists because the manifest is the application's, and because
the proof needs a source whose completions it can deliver in any order.

### 2. The determinism rule

> **Load completions only populate storage.** A finished load never installs a tile, never selects
> one, never changes an input, never expires a pin and never advances time. Readiness is read in
> exactly one place — the tick barrier — and every mutation list is applied in `TileKey` order.

Physics hands out body and shape ids in call order, so walking the *ready set* sorted is what makes
them a function of the tick history rather than of which load won.

### 3. The barrier order

One place, documented in `terrain_collision.hpp` and implemented by `plan` + `try_commit`:

| step | who | what |
| --- | --- | --- |
| 1 | application | freeze the tick's inputs; call `request_admission` / `pin` / `unpin` |
| 2 | `plan` | compute the immutable required / activate / deactivate lists — from demands, pins and the manifest, never from readiness |
| 3 | `try_commit` | request the assets the plan wants |
| 4 | | install every wanted tile that is ready **and due** (its scheduled tick has come, or a body requires it): validate, register the shape, create the static body, **release the asset handle — once** |
| 5 | | **stall check** — an admitted body's tile missing ⇒ return `Waiting`; nothing below runs |
| 6 | | evaluate deferred admissions: admit only if **every** tile under the bounds is installed |
| 7 | | deactivate outgoing tiles: destroy the body, unregister the shape (a tile still loading gives back the handle it holds here instead) |
| 8 | | journal `(tick, key, activate \| deactivate)` |
| 9 | application | run gameplay and physics |

Installs precede evictions, so for one barrier a moving envelope holds both the incoming and the
outgoing tiles.

### 4. Demands and the two envelopes

A **demand** is the box a simulated body can occupy during the tick: its bounds swept by its
velocity over `dt`, plus a stated margin (`swept_bounds`). Every simulated body contributes —
players, vehicles, debris, **sleepers included** — and so do projectile and hitscan sweeps.
**The camera never contributes**: what one client looks at must not change what the simulation
collides with.

- A tile *under* a demand is **required** this tick.
- A tile within `activate_margin_tiles` (default one tile width) is requested and installed as it
  becomes ready — the prefetch envelope.
- A tile stays until it is further than `retain_margin_tiles` (default two) from every demand, or
  while pinned. The gap is the hysteresis.

A box whose edge lies exactly on a seam reaches the tile on the far side: a body touching a seam
rests on both tiles.

### 5. Deferred admission

`request_admission(entity, bounds)` answers `Admitted` if every tile under the bounds is installed,
otherwise `Deferred`: the entity stays out of the simulation, its tiles are pinned
(`PinReason::Admission`) so they are requested at the next barrier and cannot be evicted before it
arrives, and step 6 re-asks at every barrier. Admitted entities are reported by `admitted()`; their
pin is dropped by the *next* `plan`, by which time they are demands in their own right — so there is
no barrier at which the tile is neither pinned nor under a body.

### 6. The stall is the safety net

A body that is *already simulated* cannot be held out without inventing what happens to everything
it touches (that is island freezing, which the owner ruled out). So if its swept bounds need a tile
that is not installed — the envelope was too small, or the disk too slow — `try_commit` returns
`Waiting` and the tick is not simulated. The caller pumps its loader and retries **with the same
plan**; the tick number, inputs and bodies are untouched.

It is counted separately (`stalls_admitted_body`, `stalls_sweep`, `stall_retries`) and reads zero in
every proof that is not provoking it. That zero is the claim that the envelope is sized correctly.

`Failed` is distinct from `Waiting`: a required tile whose load failed or whose content was refused
can never be waited into existence, so the commit fails explicitly instead of stalling forever.

### 7. Pins

`pin(bounds, revision, reason)` keeps every tile under the bounds wanted and resident for a reason
other than a body (`Query`, `History`). A pin does not stall the tick; its holder asks `covers`
first. The revision is the one the caller's data was built against: if any tile under the bounds is
at another, the pin is **refused**, because replaying history over different ground than it was
recorded on is the bug the revision exists to catch.

### 8. Refusals fail explicitly

| refusal | behaviour |
| --- | --- |
| stale handle | not read, not released; the tile is requested again |
| revision mismatch (payload) | not installed; the record is `Failed` and not retried while wanted |
| revision mismatch (pin) | invalid token |
| invalid content | geometry that does not fit its grid cell, or physics refused it ⇒ `Failed` |
| budget overflow | the required-or-pinned set exceeds `max_required_tiles` ⇒ the commit fails **before** anything is requested. Never trimmed: every way of trimming a required set is a way of simulating over missing ground. A non-finite or absurdly wide box is the same refusal |
| stale plan | a superseded or already-committed plan is refused; its eviction list is not applied |

### 9. The client

The same module runs over the client's physics world. The predicted body **and the authoritative
state a correction would rewind to** are demands; a barrier that answers `Waiting` blocks
reconcile, replay and predict for that tick (counted — on a client `stalls_admitted_body` *is* the
blocked-prediction count). The input is still sent. When the tile lands, ordinary reconciliation
puts the client where the authority is.

This brick's client wiring is a headless fixture with the real `Predictor` and a fixed-delay queue.
No wire protocol.

### 10. Counters (CLAUDE.md guardrail 5)

`TerrainCollision::counters()`; every field is moved by a test.

| group | counters |
| --- | --- |
| traffic | `requests`, `requests_cancelled`, `installs`, `evictions`, `load_failures` |
| schedule | `installs_held_for_lead`, `installs_required_early`, `install_late` |
| deferrals | `evictions_skipped_pinned` |
| admission | `admissions_immediate`, `admissions_deferred`, `admitted_after_deferral`, `admission_retries`, `admissions_cancelled`, `admissions_blocked_by_failure` |
| stalls | `stalls_admitted_body`, `stalls_sweep`, `stall_retries` |
| pins | `pins_taken`, `pins_released`, `pins_active` |
| refusals | `refused_stale_handle`, `refused_revision_mismatch`, `refused_invalid_content`, `refused_budget_overflow`, `refused_unknown_pin`, `refused_stale_plan`, `refused_required_failed`, `coverage_refusals` |
| residency | `tiles_installed`, `bytes_resident`, `peak_bytes_resident` |

**No per-peer "what they have" fact is introduced.** The module knows what *this* process has
installed, which it observes directly. Nothing here records what a remote peer holds, so
`docs/design/replication.md` is unchanged. The next brick does introduce one — see below.

## The activation schedule, and what "deterministic" claims

A tile requested at tick T is installed at tick **T + `activation_lead_ticks`** — not when its load
happens to finish. The default lead is **8 ticks** (review decision, fix 1; the first cut defaulted
to 0). With lead 0 the install tick is set by I/O, so the set of static bodies at a given tick — and
with it the ids physics allocates and the broadphase order — can differ between two runs with
identical inputs. That leaks into replay and into M20's "dedicated digest matches the in-tree run".

The schedule has exactly two exceptions, both counted, neither silent:

| | when | install tick | timing-independent? | counter |
| --- | --- | --- | --- | --- |
| **early** | a body requires the tile before T + lead | the tick it became required (the stall holds that tick if the load is slow) | yes | `installs_required_early` |
| **late** | the load is not finished at T + lead | whenever the disk delivers it | **no** | `install_late` (once per request) |

Nothing simulates over a late tile's gap: a body that needs it stalls the tick, an arriving entity
stays deferred. So **`install_late == 0` is the witness that a session was timing-independent**, and
a non-zero value says precisely how many installs were not.

**Why 8 — reasoned, not measured.** Nothing in this brick times a real tile load. The floor is 1–2
ticks whatever the disk does, because the asset server readies assets only at its once-per-frame
pump. 8 ticks is 133 ms at 60 Hz: several times that floor and comfortably above a warm
read-and-decode of a few megabytes of samples. A cold spinning disk can exceed it; that is what the
counter is for, and the number should be re-derived once tile loads are measured (brick 8e).

**What it costs.** An admission takes at least `lead` ticks even with an instant disk, and the
prefetch envelope must cover `lead` ticks of travel (at a 64 m tile width, 480 m/s).

Proven (`tests/terrain_collision`):

- completion **order** — FIFO, LIFO and two seeded shuffles of one session: identical journal,
  admission ticks and `world_hash()` after each of 300 ticks;
- completion **timing** — loads taking a seeded 3–7 pumps under the default lead of 8: identical
  again, with `install_late == 0` in every run;
- **a load exceeding the lead** (30 and 45 pumps): `install_late == 1`, no stall, the rest of the
  journal unchanged, hashes equal up to the scheduled tick and different from it on — the limit of
  the schedule, pinned;
- a control at lead 0: timing moves the journal, and `install_late` equals the request count.

## Consequences

- Server physics memory is bounded by where the simulated bodies are, not by the map: a kilometre
  traversal installs 195 tiles and never holds more than 15 (measured in the plateau proof).
- Spawn and teleport are no longer instantaneous in general. Gameplay must handle `Deferred`.
- The application owns demand collection. `PhysicsWorld` has no body iteration, and a module that
  enumerated bodies itself would have to know which are simulated and which are render-only.
- **An installed tile holds no asset ownership.** Physics copies the samples at registration, so
  the handle is released right after a successful install (review decision, fix 1): server sample
  memory is one copy, not two. A client's render residency holds its own ownership of the same slot
  (ADR-0067: one request, one release), so nothing is reloaded there. Reactivating an evicted tile
  loads it again — an ordinary request and an ordinary install.

## Known limits

- **Not measured.** No timing or real byte budget is claimed. `bytes_resident` counts sample bytes
  of installed tiles.
- **The cooked heightfield carries no revision** — deferred to the deformation/transport brick
  (review decision, fix 1). Until then `AssetServerTileSource` vouches only for the revision the
  manifest named *when the load was requested*; it cannot detect a file on disk that is not the
  revision the manifest says. The payload-mismatch refusal is proven against the fake source only.
- The stall holds the *whole* tick. That is the owner's decision; it is why the counter exists.
- A deferred entity whose tile is `Failed` waits until cancelled — there is no timeout policy in
  this brick. It is counted apart from an ordinary wait (`admissions_blocked_by_failure`) and
  warned about once per deferral, so a stuck admission is visible.
- A late install is *counted*, not prevented: forcing the schedule would mean stalling the server
  for a tile nobody is standing on.
- `Failed` tiles are not retried while still wanted. They retry only after leaving the retain
  envelope and being wanted again.
- The cap is on the *required-or-pinned* set. The prefetch and retain envelopes are not budgeted.
- Tiles are columns: height plays no part in which tile a box is over.
- **TSan: run, clean, narrow.** `scripts/build.sh --sanitizer` reuses `build/dev`, so a separate
  directory was configured by hand (`-DRIME_SANITIZER=thread`, dev's Conan toolchain), only
  `rime_terrain_collision_tests` built, run five times — zero ThreadSanitizer reports — and the
  directory deleted. The module itself is single-threaded by contract; the threaded path this
  exercises is the AssetServer's load jobs behind `AssetServerTileSource`, in one test case.

## Deferred — the next bricks

- **Reliable activation / lease transport, and late join.** The server ships its journal; a client
  acknowledges a tile only on **confirmed installation with a retained lease** — not on receipt and
  not on load. That acknowledgement *is* a per-peer "what they have" fact, so guardrail 5 and
  `docs/design/replication.md` apply to it in full.
- **Budgeted prefetch**: a measured byte budget and a policy for trimming the *optional* envelope
  (never the required set). Brick 8e.
- **Deformation keyed by tile revision**: crater operations in authoritative, non-evictable state;
  samples reconstructed before registration; history pins holding old revisions. Brings the cooked
  revision stamp with it.
- Prediction-history pins sized from the real replay window (the fixture pins by demand only).
- Island freezing — ruled out for now by the owner; the stall is where it would attach.

## Review decisions (fix 1, 2026-10-06)

Made by the orchestrating review as engineering calls; the owner can reverse them.

1. **`activation_lead_ticks` defaults to 8**, with `install_late` counting a missed schedule.
2. **The asset handle is released right after a successful install.**
3. **A revision field in the cooked heightfield is deferred** to the deformation/transport brick.
4. **A deferred entity whose tile failed keeps waiting**, counted separately and warned once.
5. **TSan is run** in a hand-configured separate build directory.

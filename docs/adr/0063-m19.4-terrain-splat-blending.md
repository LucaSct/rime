# ADR-0063 (m19.4): Terrain splat blending — four layers, a partition of unity, and no CI to catch us

- Status: Accepted
- Date: 2026-10-05

## Context

ADR-0060 cooked the terrain heightfield, ADR-0061 gave it convex queries, ADR-0062 drew it. All
three deal in *shape*. The ground is still one material: `terrain.frag` shades every texel the same
way, so a terrain tile reads as a single enormous slab of whatever the sample material happens to
be. ADR-0043 names **splat blending** as part of M19's scope, alongside streaming, and this is it.

"Splat blending" is the standard terrain technique: each surface texel carries weights over a small
palette of materials — grass, rock, sand, snow — and the shader blends them. The decisions worth an
ADR are not the blend itself (a weighted sum is a weighted sum) but **where the weights live, how
many there are, what makes a weight set valid, and how the result is proven** — especially now,
because of the constraint in §5.

## Decision

### 1. The weights are a v2 block in the heightfield payload, not a separate asset

`kHeightfieldPayloadVersion` goes to **2**. A v2 payload appends, after the sample blob:

- `weight_columns`, `weight_rows` (u32 each) — the weight grid's own dimensions, which need **not**
  equal the height grid's;
- a `layer_count` (u32), currently always 4 (see §2);
- four `AssetId`s (u64 each) — the tile's material palette, slot by slot, where
  `value == 0` means "this slot is unused";
- `weight_columns * weight_rows * 4` bytes of weights, row-major, x fastest, the same walk as the
  samples and the same walk a 2-D RGBA8 texture upload makes.

A **v1 payload stays valid** and decodes to a `HeightfieldAsset` with `weights.empty()`, which
means "one material, shaded exactly as m19.3 shades it". An old build meeting a v2 file still gets
a clean `UnsupportedVersion` refusal, which is what the version field was put there for.

*Why in the same asset rather than a sibling.* The weights are per-tile surface data with the same
footprint, lifetime and streaming unit as the heights; splitting them would mean two asset ids, two
load paths and two chances for a tile to draw with another tile's weights. The cost of this choice
is that re-painting a terrain's materials re-cooks its heights too — accepted, because the cook is
deterministic and byte-identical run to run (`cook_is_byte_identical_run_to_run`), so a re-cook with
unchanged heights produces an unchanged sample blob.

*Why the weight grid has its own dimensions.* Material detail and height detail are independent:
painters want a finer splat map than the collision grid needs, and a 4× finer weight map costs
nothing in physics. Tying them would force one of the two to the other's resolution forever.

### 2. Exactly four layers, u8 weights, normalized at cook time to sum to 255

Four is what fits one RGBA8 texture fetch, and it is the number every terrain pipeline settled on
for the same reason. More layers are a later ADR, and the `layer_count` field is where that
extension goes; the reader **rejects any value but 4** today rather than silently half-supporting it.

The weights are u8 and the **cook normalizes them so every texel's four weights sum to exactly
255**, using largest-remainder apportionment so the result is deterministic and exact rather than
round-to-nearest with a drifting sum. **The reader rejects a texel whose weights do not sum to 255**,
and counts the rejection.

*Why exact normalization is the reader's business.* An unnormalized splat map does not fail loudly:
it dims or blows out the surface by a few percent, which reads as a lighting bug and gets chased in
the renderer for a day. Making the sum a validated invariant moves that failure to the cook, where
it is one refused file with a counter, and lets the shader blend with no renormalization in the
inner loop.

### 3. The blend is linear in the material parameters, and height-blending is deferred

The shaded parameters are the weighted sum of the four palette materials' `base_color`, `metallic`
and `roughness`, weights normalized to 1. Not a height-blend, not a noise-perturbed transition — a
plain partition-of-unity sum.

*Why the plainest rule.* Height-blending (biasing the transition by a per-material height map so
gravel shows through grass along the crack lines) looks markedly better and is what a shipped game
wants. It is also a change to the *weights*, not to the plumbing: it reads the same four weights and
the same palette and redistributes them before the sum. Landing the plumbing with a rule that is
trivially checkable, and then changing one function, is cheaper than landing both at once and
having no way to tell a plumbing bug from a blend-curve bug. Named here so it is a deferral and not
an oversight.

### 4. The proof is a partition of unity, which needs no margin

The structural property: **if all four palette slots name the same material, the blended result must
be bit-identical to the single-material path, for every weight combination.** A sum of weights that
do not reach 1 darkens; one that exceeds 1 blows out; a transposed row-major walk picks up a
neighbour's weights; a forgotten slot drops a term. All four show up as a difference from the
one-material render, at every texel, with **no tolerance to tune** — unlike a colour comparison
against an expected blend, which needs a margin and therefore hides small errors inside it.

That is the anchor. Beside it: a texel at `(255, 0, 0, 0)` must equal layer 0 exactly; a texel at
`(128, 127, 0, 0)` must sit between layers 0 and 1 on every channel and equal neither; and the
refusal counters must move on an unnormalized file, a `layer_count != 4`, and a weight blob whose
length disagrees with its dimensions — a drop that is not counted is a drop nobody sees.

### 5. Every gate runs locally, because there is no CI until 2026-11-01

The repository's GitHub Actions allowance (2000 minutes/month) was spent on 2026-10-05 and does not
reset until **1 November**. Pushing this brick produces **no verification at all**. So:

- the full local gate set runs and is reported in the PR: build as its own command checking `$?`,
  `ctest --preset dev`, `clang-format --dry-run --Werror` over CI's exact `find` set, and from
  `tools/`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`;
- the sanitizers run locally too (`scripts/build.sh --cpp-only --sanitizer address`), since the
  ASan/UBSan and TSan jobs will not;
- every new translation unit gets `clang++ -fsyntax-only`, which is now the **only** Clang coverage
  that exists — the TSan job was the matrix's single Clang build;
- **macOS and Windows have no local substitute on this machine and are simply unverified.** This is
  not hypothetical: CI caught exactly this class of bug on m19.1a nine hours ago, where an assertion
  that held on x86-64/GCC failed on macOS/arm64 because float rounding put two rays on the other
  side of a seam (ADR-0060's addendum). The lesson is written into §4 above — prefer a property
  that holds on every target, like a bit-identical partition of unity, over a number measured on
  one.

## Consequences

- A v2 heightfield carries its own material palette, so a terrain tile is self-contained: one asset
  id gets you a surface that collides *and* shades correctly.
- `HeightfieldAsset` grows `weight_columns`, `weight_rows`, `layers[4]` and `weights`; v1 files
  decode with an empty `weights`, and every existing test and fixture stays valid.
- **The schema hash does NOT change, and must not.** `heightfield_schema_hash()` is the reflection
  hash of the *fixed header record*, which v2 leaves alone: everything new is appended after the
  sample blob and discriminated by the payload version. That is precisely what the version field
  was added for, and it is what lets §1's promise hold — a v1 file keeps reading. Changing the
  schema hash instead would reject every existing cooked terrain, including the cross-language
  fixture (`fixture_test.cpp`, `terrain.rhf`), which stays valid and stays the drift alarm; it only
  needs re-cooking once the cook starts *emitting* v2.
- Deferred, deliberately: height-blended transitions (§3), more than four layers (§2), per-layer
  normal maps and UV scales (the palette holds material ids, and a material already carries its own
  maps), and streaming the weight map separately from the heights (ADR-0043's streaming brick).

## Addendum (2026-10-05, the cook's input — step 1 landed)

How the Rust cook (`tools/asset-pipeline/src/heightfield.rs`) is told about splat materials,
decided while implementing step 1. All of it is cook-side input format, cheap to change, and none
of it touches the payload contract above.

- **The palette is four optional sidecar keys, `layer0`..`layer3 = 0x<hex>`** — the cooked
  material's `AssetId`, the same content-hash reference `material.rs` uses for textures. Hex only,
  nonzero, no duplicates, `layer0` required once any layer is named. This keeps the sidecar parser
  string-free; resolving material *paths* to ids belongs to the manifest, not to a heightfield
  sidecar.
- **The weights come from a sibling `<stem>.splat.png`, 8-bit RGBA only** (R..A = layer 0..3),
  decoded by the `image` crate the texture cook already uses — no new dependency. Its own size is
  the weight grid's size.
- **No `layerN` key → v1, byte-identical to before** (`terrain.rhf` did not change). Layers without
  a splat map, and a splat map without layers, are both refused: a forgotten layer list must not
  silently drop a painted map.
- **Refused rather than guessed:** a nonzero weight on an unused slot, and a texel with no weight
  on any used slot. Each message names the texel.
- **Normalization is integer largest-remainder apportionment**, ties to the lowest channel index;
  a texel already summing to 255 passes through unchanged. Pinned across languages by the new
  `terrain_splat.rhf` fixture (3×2 weights over a 5×4 height grid), which the C++ reader loads
  with exact expected integers.

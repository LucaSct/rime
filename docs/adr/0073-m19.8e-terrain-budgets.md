# ADR-0073 (m19.8e): Terrain streaming budgets — bytes, an upload cap, culling, streamed bakes — and the travel envelope, measured

- Status: Accepted
- Date: 2026-10-06
- Number: provisional (0068 is m19.8c's, on its own branch). Renumber at merge if it clashes.

## Context

M19.8 streams terrain in five bricks (ADR-0067's plan). 8a bounded GPU residency by a **slot
count** and said bytes would be "measured, not enforced (8e)". 8d2 pinned a root cover so pressure
lowers detail, never coverage, and listed for 8e: measure CPU/GPU ms and upload bandwidth, frustum
culling, a byte budget, tuning for travel speeds. 8d3 added appearance bakes and recorded two gaps:
a bake's CPU copy was never released (bakes were the AssetServer's *retained* kind, so every parent
ever loaded kept 8·N² bytes of RAM until the server died), and its GPU proofs drew a synthetic
bake written by C++, never one the real cook produced.

This brick closes M19.8. The scope was decided in its spec; this ADR records it as built and what
was measured.

## Decision

### 1. Bakes go through the streamed asset path

`AssetServer` gains a third streamed kind, **textures**: `request_streamed_texture(path)` returns a
`StreamedTextureAssetHandle` with ADR-0067's contract unchanged — one ownership per request,
evicted by the last release, generation-checked, deferred under an in-flight load. A different
handle type from the retained `TextureAssetHandle`, so the two can never be confused.

`TerrainResidency` requests a parent's two bake textures this way and **releases them the moment
the pass has its own copy** (`set_bake` copies the texels) — or when the bake is refused, fails to
load, or the tile is forgotten. A resident tile never holds a bake's CPU copy; the gauge
`resident_bake_holds` says so every frame. `AssetServer::resident_streamed_bytes()` counts the
decoded payloads the streamed pools hold, raised at publish and lowered by exactly as much at
eviction — the number "the CPU copy was released" is measured in.

The layer textures stay retained (ADR-0067 §5, ADR-0069): they are a small shared set, and moving
them is the builder's "dependent loads" item, not this brick's.

### 2. A byte budget, on top of the slot budget

`TerrainResidencyConfig::byte_budget` (0 = none) covers everything terrain residency puts on the
GPU: every **occupied and retiring** slot's tile bytes (`TerrainPass::tile_bytes`: heights,
indices, weights, uniform block, bake) plus the builder's live **layer textures**. Retiring slots
count because their memory is not free until the fence says so.

- **Admission by prediction.** `TerrainPass::predicted_tile_bytes` computes a tile's bytes before
  anything is allocated (the test asserts it equals `tile_bytes` after the upload, for every tile);
  a tile is uploaded only if the committed bytes plus its prediction fit. `TerrainLayerBuilder::
  update(handle, allowance, created)` creates a layer texture on the GPU only within the headroom
  left after the tile's own bytes, so a palette can never push the total past the budget either.
  The gauge `budget_bytes` therefore never exceeds the budget — not "comes back under", never over.
- **The root cover is reserved inside it,** exactly as its slots are (8d2): a non-root's limit is
  the budget minus the predicted bytes of every root still waiting. A root's bytes are predicted
  from the grid alone (a parent: no splat; a bake if its manifest line names one). A world whose
  roots alone exceed the budget is **refused at construction**, counted in
  `byte_budget_refusals`, and draws nothing — no budget can honour "never a hole" then.
- **Under pressure detail is lowered, never coverage.** A tile that does not fit evicts resident
  tiles of lower priority — 8d2's victim rule: not wanted, then prefetch, then wanted tiles behind
  it; never a root, never a parent for its own child — until it would fit, counting the bytes of
  victims still retiring as on their way rather than evicting more for them. Otherwise it waits,
  counted per tile-frame in `byte_budget_waits` and in the new miss reason `over_budget`. A tile
  that is not resident is simply not usable, so the selection draws its parent: the 8d2 fallback.

### 3. A per-frame upload cap

`upload_cap` (bytes per frame, 0 = none) bounds tile and layer-texture uploads. Uploads happen in
the existing advance order — priority class (roots, wanted, prefetch), then the distance of the
tile's parent box (nearest first), coarser first, ties broken by key — and **the first tile that
would cross the cap closes it for the frame**: it and every later one wait, counted in
`upload_cap_waits` and the miss reason `upload_capped`. A smaller, farther tile never overtakes a
nearer one that did not fit; the order of waits is therefore a function of the camera path alone.
A tile larger than the whole cap may go as a frame's **first** upload, counted in
`oversize_uploads` — otherwise it could never stream at all. An optional `journal` records every
upload and every wait, in order, with its bytes.

### 4. Frustum culling of the selected leaves

`frustum_cull` (opt-in) culls a leaf whose **cooked box** — the tile's footprint × the manifest's
`min_y..max_y`, which bound every level-0 sample beneath it (ADR-0070) — is wholly outside the
view: all eight corners beyond one clip plane, in Vulkan's 0..1 depth. The cooked box rather than
the tile's own samples: it is what the selection measures distance to, it needs no CPU heightfield
(level-0 tiles release theirs at upload), and it contains whatever the tile draws, including the
morph toward its parent (a subsample of its own). Culling changes **draws only**: the selection,
requests, uploads and evictions are decided before it, and a culled leaf's slot (and the parent
bake it would have borrowed) is still marked read, so even the fence bookkeeping is identical with
culling on or off. Off by default because every m19.8d proof counts draws against the selection.
Counted: `culled_draws`, and `visible_fallback_draws` (fallback leaves actually drawn).

### 5. An end-to-end cooked world

`tests/assets/fixtures/splat_world/` holds sources (`gen_splat_world.py`) and **only bytes the
`rime` CLI wrote** (`regen.sh`): a material (`rime cook`), two terrain layers with textures and
height blend (`rime terrain-layer`), and a 4×4, 3-level world with five baked parents (`rime
terrain-world`). `cook_fixture.rs` pins it byte for byte. The engine streams it through
`TerrainResidency` and the real `TerrainLayerBuilder`, with no C++-written asset anywhere.

### 6. Counters (guardrail 5)

| counter | counts |
| --- | --- |
| `budget_bytes` / `peak_budget_bytes` | gauge: tile bytes (resident + retiring) + layer textures |
| `layer_texture_bytes` | gauge: the builder's live layer textures |

| `upload_bytes`, `upload_bytes_this_frame`, `peak_upload_bytes_frame` | tile + layer-texture bytes uploaded |
| `upload_cap_waits` / `oversize_uploads` | tile-frames waiting for the next frame's cap / tiles sent alone over it |

## Measured budgets — UNPINNED (`docs/perf/m19.8e-terrain/`)

`samples/15-terrain` flies a generated 4 km world (32×32 tiles of 65² samples at 2 m, 6 levels,
1365 tiles, cooked by `rime terrain-world`) one way at each speed, paced to 60 Hz, warm-started,
with culling on, at 1920×1080, τ = 1 px. **The GPU clocks could not be pinned** (no
non-interactive sudo); `perf.sh` measured the 3060's graphics clock at 412–1942 MHz and refused to
file. The GPU columns are therefore indicative; counts and CPU columns are not clock-bound. **To be
pinned by the owner** (`scripts/perf.sh --sample terrain --commit`).

RTX 3060, budget 96 MiB, cap 256 KiB/frame (release build):

**The travel envelope** — the fastest speed with fallback under 1 % of drawn leaves *and* ≥ 95 % of
frames fitting 16.67 ms of residency + terrain GPU — is **300 m/s** for 96 MiB and 256 KiB/frame,
on the RTX 3060 and on RADV alike (the counts are identical to the leaf: the policy is
deterministic, and on pace the fallback is set by the cap). With a **1 MiB** cap it is **30 m/s on
the 3060** (pace: a ~1 MiB upload frame costs 30–60 ms of synchronous uploads) and **2400 m/s on
RADV** (residency p99 ≤ 2.6 ms). So the cap is the knob, and its right value is machine-dependent
until uploads are asynchronous.

**Bytes per slot, exact:** level-0 splat tile 108 070 B, parent 140 718 B (bake 33 800 B = 8·N²);
the per-tile u32 index buffer is 98 304 B of either — 91 % / 70 % — and the same for every tile.

**Budgets adopted** (defaults of the sample, and the starting point for a game): 96 MiB of terrain
GPU memory, 256 KiB/frame of uploads on a discrete GPU, culling on. MEASURED on the machine above,
unpinned; to be confirmed pinned by the owner.

**Policy decisions taken here.** A parent still waits for its bake under pressure (8d3 asked): its
bake now loads on the streamed path alongside the heightfield, and in the sweeps above no parent
was drawn without one; a parent shown in the placeholder first would be the pop 8d3 removed. τ and
the morph fraction stay at 8d2's defaults; μ is set to one frame's step at the travel speed.

## Consequences and known limits

- Terrain GPU memory and per-frame uploads are now bounded in bytes, coverage still never lost;
  bakes no longer live in RAM after upload.
- **Uploads are synchronous** (`TerrainPass::upload`: several blocking writes per tile). On the
  3060 this, not bandwidth, is what limits the cap. Inferred cause (not profiled): each write is a
  staged copy the frame waits for, across PCIe; RADV's UMA writes are ~20× cheaper.
- **One index buffer per tile**, identical for all: 70–91 % of every tile's bytes. A shared index
  buffer per grid size would cut terrain GPU memory about 4× at no other cost.
- **One raster pass per drawn leaf** (~100 at 1080p): each is timed, none untimed, but the per-pass
  overhead was not separated from shading, nor was the bake-fetch cost 8d3 named.
- The cap closes strictly in priority order: a large tile at the head of the queue holds back
  smaller ones behind it for a frame (head-of-line blocking), by design — determinism and
  nearest-first over throughput.
- Layer textures are counted whole: a builder shared by two residencies is charged to both.
- LOD parents keep their CPU heightfield while resident (2·N² bytes each, for the 8d1 pair
  checks) — counted by the server (`resident_streamed_bytes`), not budgeted.
- Culling is opt-in and LOD-only; a level-0-only (8a) world draws every resident tile.
- The world and path are one generated case; the envelope moves with roughness, τ and FOV.

## What M19 still has to close

- **8c** (regional collision, its own branch) to land and be reconciled with this residency.
- **Pinned measurements** of the table above, filed by `perf.sh --commit`, and the budgets
  confirmed from them.
- **Asynchronous uploads** (staging ring, transfer queue) — what lets a discrete GPU use the
  larger cap RADV already can, and the largest lever on the envelope.
- **A shared index buffer** and **batched leaves** (one pass, or indirect draws) — memory ÷ ~4 and
  the per-pass overhead.
- A **detail-preserving far appearance** (8d3's known limit) and **layer textures on the
  streamed path** (dependent loads).

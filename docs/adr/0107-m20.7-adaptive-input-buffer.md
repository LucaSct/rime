# ADR-0107: m20.7 — an adaptive server input buffer: stall instead of discard, drain by client dilation

- Status: Accepted (owner, 2026-10-26: accept, make `adaptive` the default, and move the existing two-process
  proofs onto it — built opt-in overnight first, so the default flip is its own reviewable commit)
- Date: 2026-10-26
- Extends: ADR-0103 (InputV2: redundant input, server jitter buffer, execution ack)

## Context

ADR-0103's jitter buffer starts after `slack_ticks` commands and then retires exactly one client sequence per
server tick, applied or synthesized. Retiring on schedule is what makes a lost command cost one stutter, but it
also makes **any lateness permanent loss**: when the client's command for a slot is not there yet, the slot runs
a stand-in and the real command, arriving a moment later, is thrown away as late.

That is what reddens the two-process proofs on slow hosted runners and what the owner felt in play:

- `hello_game_play_interaction` on macOS-latest at **loopback** (#353, job 121315134246): 97 checkpoints where
  the server's player disagreed with the client's because of a lost-or-late input, on a link that loses nothing.
- #352 on windows-latest: `hello_game_net_proof` applied 48 of 240; macOS: the throw proof's late-alive gate.
- A client frame hitch of k ticks (a stall, then a catch-up burst; `network_client.cpp`'s loop sleeps until the
  next deadline and runs back to back when behind) loses k commands, whatever the slack.

Measurement debt found on the way: the server's `late` counter counts every command whose sequence is already
past, which includes the two redundant copies every packet carries. The owner's session read late 13 240 vs
applied 6 274 (≈ 2.1×, i.e. mostly redundancy); nothing measured how many commands actually **missed** their slot.

## Decision

### 1. Count what missed, separately from what was redundant

`late_missed`: a late command whose retired slot ran a stand-in (its applied-mask bit is 0). `late` keeps its
meaning. Both modes. Without this the problem cannot be measured, and a proof of the fix cannot see it.

### 2. Adaptive mode: an empty buffer STALLS, it does not retire

When the next sequence is not held:

- **nothing later is held** (the client is behind, or silent) → **stall**: run a neutral stand-in, retire
  nothing, shift no mask bit. The client's sequence time slips one tick behind server time; the command, when it
  arrives, is applied, not discarded. Neutral, not the held axes repeated: the player's trajectory then remains a
  function of the command sequence alone, so a stall costs no correction of the player's own path (held axes
  would move it a tick further than the client predicted, and the real command later would move it again).
- **a later sequence is held** (a genuine gap: every redundant copy lost, or heavy reordering) → retire it as
  synthesized, exactly as ADR-0103 does.

This is the playout-buffer rule of voice and video jitter buffers (grow on underrun), and it is lossless across
a client hitch: the hitch becomes k stall ticks and k ticks of extra buffering.

Guardrail 5 holds: `retired_through` still advances only on a retirement, and a mask bit is still set only for a
command that executed. What changes is that a client gone silent no longer has its sequences retired by server
time; nothing consumes that progress for a silent client (the client window prunes on results it receives).

### 3. The client drains surplus by dilating its own tick, never the server by dropping

A buffer that only grows adds input delay for good. Dropping commands to shrink it would lose presses and cost
corrections; Overwatch and Unity Netcode for Entities instead have the **client** run slightly slower or faster
so its commands arrive at the depth the server wants. Here the server reports, every tick, an `InputPacing`
message (new tag `0xE7`, its own unreliable stream): the margin after the step (contiguous commands still held)
and a running stall count. A pure client leaf, `InputPacer`, watches a window of reports and, when the minimum
margin across a whole window with no stall exceeds the target, lengthens the client's tick period by 1/16 for 16
ticks per tick of surplus — each tick of buffer drained, losslessly, in about a quarter of a second of 6 % slow
motion — then waits for a fresh window. The whole surplus goes in one episode: the window minimum is a lower bound
on the margin, and nothing but a stall (which only adds) changes it during the window, so this cannot undershoot. It never speeds the client up: underrun is handled by §2 on the server.

Asymmetric on purpose: growth is immediate and lossless (a stall), shrinkage is slow and lossless (dilation),
so jitter settles the buffer at its own depth and a single hitch costs a few seconds of extra delay, not inputs.

### 4. Opt-in until the owner decides

`dedicated --input-buffer fixed|adaptive`, default `fixed`: every existing proof, digest and counter is unchanged.
The client dilates only when pacing reports arrive. Whether `adaptive` becomes the default, and whether the
existing proofs move to it, is the owner's call after the proof below.

### 5. The proof

`hello_game_play_adaptive`: two processes, a scripted client hitch (`play --debug-hitch T:MS`, off by default),
loopback and impaired. Gates: with `adaptive`, `late_missed` 0 and every command the client sent after the start
applied; stalls ≥ the hitch's ticks; the margin drained back under the target + 1 within a bound derived from the
pacer's constants; equal digests. Control that must fail: the same run with `fixed` loses ≥ the hitch's ticks
(`late_missed` > 0).

### 6. Bricks

m20.7a, the pure leaf (adaptive mode, `late_missed`, the pacing codec, `InputPacer`); m20.7b, the wiring
(`--input-buffer`, the pacing stream, client dilation, `--debug-hitch`, counters in the `finished` JSON); m20.7c,
the proof.

## Consequences

- With `adaptive`, the server tick and the client sequence drift apart by the stall count; anything that maps
  one to the other by subtraction is wrong there. The reconciler replays by sequence and is unaffected.
- A stall moves the world without the player, so objects the player touches (the m20.6 crate) can read a small
  correction at a stall. Counted, not hidden.
- Not here: per-client buffers for multi-client (one schedule per admitted session already), speeding the client
  up, and choosing the default.

## Addendum — accepted as the default (2026-10-26)

The owner accepted this ADR and chose §4's open question: `adaptive` is the `dedicated` default, and the existing
two-process proofs (connect, throw, interaction, net proof) run on it with no flag. `--input-buffer fixed` stays
as the control (`hello_game_play_adaptive`'s third leg passes it explicitly). The motivation is the hosted-runner
reds of §Context; whether the default greens macOS is measured by the first CI run, not assumed.

## Addendum — review fixes before the default ships (2026-10-26)

An astra (gpt-6-astra) review, verified against the code, found three things:

- **A wedge.** After an outbound blackout of ≥ ~61 commands every resumed command lands ≥ `next_ + 64`, is refused as
  `future`, nothing is ever held, and §2's stall never ends — the player froze until the session timed out. Fixed:
  when such a command reaches an EMPTY adaptive ring, the schedule RESYNCS — the skipped sequences retire unapplied
  (mask shifted, `resync_retired`), `next_` jumps to the command, counted `resyncs`. With anything still held it
  keeps refusing; the held commands drain first.
- **An unbounded drain.** One window could dilate the client for up to 992 ticks; now ≤ 16 ticks of buffer per
  episode, and a stall reported during an episode cancels it (`drains_cancelled`).
- **§Consequences overstated** "the reconciler replays by sequence and is unaffected". Replay is by sequence, but a
  stall after a checkpoint makes the next command execute later than `checkpoint.server_tick + 1`, so ages,
  cooldowns and crate contacts are corrected at the next checkpoint — corrections, not desync.

Separately, every production process used the transport's constant salt seed; client and server now seed it from
OS entropy (an input to the net layer, as its own comment requires).

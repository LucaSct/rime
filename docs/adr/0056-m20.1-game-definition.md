## Context

ADR-0046 §1 wants an exported game's *end user* to pick at launch between `play`, `browser`,
`stream`, `host` and `dedicated`, from one binary, with the mode decided before any RHI device exists
so a dedicated server never touches Vulkan. It named the load-bearing risk: that a game's play loop
can be lifted out of its sample `main` into an engine-owned `GameDefinition` *without rewriting the
game*. Until m20.1 every sample owned its whole `main` — its own flags, its own `Application`, its
own decision whether to make a device.

## Decision

**1. The split.** `rime/app/game_definition.hpp` draws the line:

| the game supplies | the engine owns |
|---|---|
| a component registrar and an optional entry `.rscene` | argument parsing and the launch mode |
| `Game::setup` — build the simulated world | the loop and the fixed tick |
| `Game::fixed_tick(TickContext&)` — one step, from an `ActionState` | whether a device exists |
| an `InputMap` (keys → numbered axes/buttons) | events → `ActionState`, and when it applies |
| optional `present_setup` / `present_frame` | the `SceneRenderer`, the window, presentation |
| optional `autopilot()` and `state_digest()` | the `RunReport`: ticks, frames, what was skipped |

`Game` is an **interface** (a game has state; a bag of lambdas sharing it is an object with its
methods scattered), created fresh per run by `GameDefinition::create`. Plain C++ compiled into the
game's own target — no scripting engine, no runtime loading, nothing in `engine/` names a game.

**2. The simulation never sees a device.** `setup` and `fixed_tick` receive a `World`, the job system
and an `ActionState`. Presentation is separate hooks, called only in a mode with a device, and must
not change what the simulation computes. The fixed-tick contract: `TickContext::dt` is the same
constant every tick, `tick` counts the game's own steps, and the step runs in the `PostSim` position
(where `on_fixed_tick` always ran), so structural world changes are legal in it.

**3. Input is actions, never keys.** A fixed `ActionState` (8 axes, 32 buttons, held + pressed-edge
bits) rather than named actions: it is copied per tick and will one day cross a network, and a game
names slots with its own constants. The engine maps each frame's events once, in that frame's first
tick (removing the one-frame lag a render-callback mapping has) or, for a zero-tick frame, in its
render (so no keystroke is dropped). Press edges latch until a tick consumes them.

**4. Modes.** `parse_launch` is a pure function of argv; the mode word is positional-first.
`mode_uses_device()` is the single answer to "may this mode touch the GPU" — false only for
`dedicated`. The runner builds its `Application` with `gpu = mode_uses_device(mode)`; in `dedicated`
the device factory (injectable via the new `AppConfig::device_factory`) is therefore never entered.
`play` and `dedicated` are real; `browser`, `stream`, `host` parse and return
`RunStatus::NotYetImplemented` (exit code 3) **before** constructing anything, naming themselves —
a stub that silently ran `play` would hand a user a window when they asked for a server.

**5. `play` without a device still plays.** It degrades to the simulation and counts every skipped
presentation (`RunReport::presentation_skipped`) — the simulation is the game.

## Proof

`hello_game --dedicated-proof` (ctest `hello_game_dedicated_proof`) runs the game five ways — the
pre-port hand-rolled loop, `dedicated`, `play` with a factory answering null, and (last, where a
device exists) `play` with a real one — at 120 ticks (mid-game) and to the win, and requires one
digest. Dedicated must report zero factory calls and zero presentation calls, and on Linux
`/proc/self/maps` must show no `libvulkan` after every GPU-free leg. Both halves were falsified
(forcing `gpu = true`; nudging the crate in `present_setup`) and went red.

## Consequences and what is not decided

- **Not link-time GPU-free.** One binary must do `play` *and* `dedicated`, so the render path is in
  the executable by design; `rime_app_game` links `rime::render`. The guarantee is at run time: the
  factory is never entered, and volk only `dlopen`s the loader inside it (`ldd hello_game` lists no
  libvulkan). A render-free server-only target would need `Application` split into a sim core and a
  render layer — possible, not needed for ADR-0046's one-binary shape.
- **A presentation hook can still perturb physics by accident.** `PhysicsSync` binds bodies in ECS
  archetype order, and `present_setup` adding `MeshRef` moves entities between archetypes before the
  first bind. hello-game's order happens to survive it (the GPU leg proves it for this game); binding
  in entity order would make it true by construction. Recorded, not fixed here.
- Network input for `dedicated`, the listening modes, a launcher UI for the no-argument case,
  content resolved relative to the executable, and bundling are later M20 bricks.

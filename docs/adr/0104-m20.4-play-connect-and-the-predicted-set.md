# ADR-0104: m20.4 — `play --connect`, and prediction as a declared predicted set

- Status: Accepted (owner, 2026-10-24; prediction scope decided by gpt-6-astra at the owner's request)
- Date: 2026-10-24
- Extends: ADR-0103 (m20.3 network input), ADR-0056 (m20.1 `run_game`)

## Context

m20.3 made `dedicated` a server a remote client can drive: InputV2 commands in, an execution
acknowledgement (`retired_through` + applied mask) out. Nothing yet comes back the other way, and
nothing on the client side is a game: the m20.3 proof's client is a test process that replays a trace.
M20.4 is the first real client — `play --connect HOST:PORT` — so a second machine on the LAN can play
against a dedicated server.

What exists (read from source by the m20.4 scoping consult, `reports/rime-oct24-m20.4-scope/out.md`):
generic ECS replication with acknowledged baselines and budgets (`ServerReplicator` /
`ClientReplicator`), remote-transform interpolation, and M12's prediction and reconciliation. But
M12's `Predictor` is built around the block's `CharacterState` and physics queries, so it serves games
that adopt that controller, not an arbitrary `GameDefinition`. And `GameDefinition` today maps a
command to actions and nothing more: a game has no way to say what it replicates or what a client may
predict.

## Decision

### 1. Prediction scope: the local player only, through a contract shaped as a PREDICTED SET

The owner asked gpt-6-astra to decide (`reports/rime-oct24-m20.4-scope/predict.md`, web sources
accessed 2026-10-24). The decision, and the staged path it belongs to:

| brick | predicted | why it is here |
|---|---|---|
| **m20.4** | the local player's locomotion and its complete controller state | establishes connection, ownership, coherent checkpoints, correction/replay and bounded recovery on the smallest set that can be wrong |
| m20.5 | + own weapon/ability state and ONE simple predicted projectile | speculative spawn, rejection and event de-duplication, without rigid-body coupling (Source's opt-in predicted weapons are the precedent) |
| m20.6 | + ONE bounded interaction group (the player and a door, or an isolated crate) | dependencies admitted together and restored atomically; contention handled; fall back to authority over budget |

Whole-world rollback (GGPO, Photon Quantum) is rejected for these bricks: it needs fully deterministic,
fully serialisable simulation, and Rime's destruction is neither bit-exact across builds (CLAUDE.md
records macOS and Linux flipping the same gate) nor small. Unity Netcode for Entities' explicit
owner-predicted / predicted / interpolated classification is borrowed; an automatic "everything I
touch is predicted" rule is not.

So that m20.5 and m20.6 extend the contract instead of breaking it, m20.4's contract is a predicted
**set** that happens to hold one entity: generation-safe identities and a membership epoch; per-entity
capture/restore plus group-level state (RNG, timers, anything hidden), restored atomically; a set
simulation step taking decoded commands, the fixed timestep and an explicit simulation tick; a
tick-addressed, read-only query environment (replay never reads interpolated render poses); and
bounded history, entity and replay budgets with an authoritative reseed when they are exceeded.

### 2. What is never predicted

The appearance of a player's own shot may be predicted later — muzzle flash, tracer, tentative impact
particles, removable decals. **Damage is never predicted**: no speculation changes health, fracture
topology, structural connectivity, collision holes, authoritative debris, score or damage-op order.
Applying confirmed damage ops is authoritative reconstruction, not prediction. Changed collision
geometry invalidates affected prediction history (or supplies the right historical revision).

### 3. Reconciliation uses m20.3's execution acknowledgement

The server sends one atomic **owner checkpoint** per tick it publishes: the predicted set's full
authoritative state plus that tick's `InputResult`, on its own named stream. The client restores the
checkpoint and replays only the commands after its `retired_through`. A retired command is never
replayed, whether it was applied or synthesized; the applied mask distinguishes exact execution from
substitution and drives diagnostics. A newer standalone result may prune the retransmission window but
must not discard history an older, still-unapplied checkpoint needs. Input sequence, server tick and
replication version are three coordinates and are never equated.

### 4. Everything else: authoritative ECS replication, interpolated

The rest of the world reaches the client through `ServerReplicator` / `ClientReplicator` — reliable
structure, acknowledged-baseline deltas — and is presented through interpolation. The client's mirror
and its prediction are separate: presentation binds server identities, it never creates duplicate
simulated entities.

### 5. The client CLI

`mygame play --connect HOST[:PORT]` (default port 7463, ADR-0103). `--no-gpu` runs a connected client
with no device at all — for CI — and `--headless` keeps its one meaning, off-screen rendering (owner,
2026-10-24).

### 6. The proof

A GPU-free two-process CTest runs the REAL `hello_game play --connect 127.0.0.1:<port> --no-gpu` path
against a `dedicated` child: a fixed input tape, then authority frozen at a named final tick while the
network drains; equal non-zero digests computed independently from each side's installed state,
differing from a zero-input control; no device or presentation calls and no `libvulkan` in either
process. Repeated with prediction on and off under the same deterministic delay/loss schedule: own-input
response within one tick with prediction, at least the round trip without, and corrections and replays
observed (not merely possible). Final-state agreement alone must not pass a client that rubber-bands
throughout — correction magnitude and replay cost are bounded gates. Negative gates: schema and
timestep mismatch, malformed and oversized state, an unreachable server, a second client, a stale
incarnation, a lost or reordered checkpoint against its ack, history exhaustion (reseed observed), and a
delta that arrives before its spawn.

## Consequences

- hello-game must hold every digest-relevant fact in replicated components; today ticks, score,
  collection times and the player's position live outside them (`samples/hello-game/game.cpp:203`).
- M12's block-specific predictor stays as it is; 99-the-block adopting the generic contract is later.
- Not in m20.4: multiple clients, `host`, predicted projectiles, interaction groups, destruction over
  this path, authentication, Windows coverage of the two-process proof (no child-process helper yet).

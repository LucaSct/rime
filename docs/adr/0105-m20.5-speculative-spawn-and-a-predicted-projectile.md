# ADR-0105: m20.5 — speculative spawn, and one predicted projectile

- Status: Accepted (owner, 2026-10-24: gameplay payoff "hit a fixed target, score")
- Date: 2026-10-24
- Extends: ADR-0104 (m20.4 predicted set), ADR-0103 (InputV2)

## Context

ADR-0104's staged path puts **own weapon/ability state and one predicted projectile** at m20.5. The m20.4
contract handles a second *already-identified* predicted entity: generation-safe ids, whole-set
capture/restore, epochs, bounded replay. What it cannot express is an entity the client creates **before
the server has said it exists** — a projectile launched on the tick the player presses the button, which
the server may accept (and then name with its own `NetId`), reject (out of ammo, still cooling down), or
accept and end before the client ever sees it. And `replaying` can suppress effects during a replay, but
it cannot stop a launch sound or impact effect from playing twice when the authoritative replica
arrives. Scoping (gpt-6-astra, read-only, `reports/rime-oct24-m20.5-scope/out.md`) measured both gaps
and proposed the design below; Valve's Source SDK's opt-in predicted weapons are the precedent for
prediction-aware weapon state and sound filtering.

## Decision

### 1. A speculative spawn has a key the client chooses and the server echoes

`SpawnKey = (session incarnation, input sequence, slot)`. It exists before any `NetId` does, a replay of
the same command recreates the same key, and a reconnect (a new incarnation) can never collide with a
key from the old session. The server attaches the key to the launch it accepts and reports a **durable
outcome** per key — `accepted → NetId`, `rejected → reason`, or `accepted and ended` — carried in the
owner checkpoint and retained until the client has acknowledged it.

### 2. Authoritative roster, provisional overlay

The checkpoint (through a negotiated, additive extension — the m20.4 codec and API stay valid) installs
the authoritative predicted roster, the ability state (charges, cooldown) and each projectile's state
atomically. A server-side membership change advances the epoch; client-side speculative entities are an
**overlay** that never changes the epoch. Reconciliation restores the authoritative roster, removes
speculation that the outcomes resolved, then replays the unretired commands — recreating the provisional
entities those commands launch, under the same keys.

### 3. Exactly-once presentation

A **presentation ledger** keyed by `(SpawnKey, event kind, ordinal)` lives outside rewindable state.
Confirmation ADOPTS the presentation already playing; rejection cancels removable effects and the
resources come back through the restored ability state; a confirmation that arrives after the predicted
projectile already expired binds the authoritative replica if it is still alive and otherwise stays
absent — a launch animation is never restarted. Damage, hits and score stay authoritative (ADR-0104 §2).

### 4. The test vehicle: hello-game's Throw

Three charges, a 60-tick cooldown, at most one live projectile, fixed launch velocity and gravity, a
45-tick lifetime, no bounce. A **server-only** swept hit against a fixed target awards one point and ends
the flight. Launch, resource use and flight are predicted; acceptance, identity, the hit and the score
are authoritative.

### 5. The proof, and the failure it exists to catch

The worst failure is invisible to a final digest: two identities surviving confirmation — a ghost
projectile, or an effect played twice. So beyond the two-process digest gate (equal, non-zero, differing
from a no-throw control) and a launch-response gate (≤ 1 tick predicted vs the round trip without, with a
sensitivity control that presents authority while prediction runs), the proof gates **at most one live
presentation per key** and **exactly-once event counts** on every tick, through replay, reordering and
expiry — and disabling adoption/de-duplication must fail it. Semantic faults are injected after session
decoding, with a counter per case: the server refuses a launch the client allowed (ammo 0, cooldown);
one copy of the launch command lost (redundancy recovers, once); every copy lost until retirement (no
launch, no resurrection on replay); a duplicated confirmation (one projectile, one effect, one point);
confirmation after predicted expiry, both with the authoritative projectile alive and already ended.

## Consequences

- The application layer stops being single-entity: server checkpoints, the client's prediction world and
  presentation all handle a roster.
- `TickContext` gains authoritative command provenance (the executed sequence, incarnation, and whether it
  was applied or synthesized), which the server needs to build a `SpawnKey`.
- Not here: predicted hits or damage (never), more than one projectile type, interaction groups (m20.6).

## Addendum — what m20.5 proved, and what it did not (2026-10-25)

`hello_game_play_throw` (POSIX two-process; real `dedicated` and real `play --connect --no-gpu
--input-tape-throw` over loopback UDP; `samples/hello-game/throw_prediction.py`) measured, on nextos, 3 of 3
runs green at ~41 s:

- **Baseline:** client and server digests equal, nonzero, and different from a no-throw control; server
  `spawn_accepted` 1, client `spawn_adopted` 1, acks sent == applied, one Launch, one End, live max 1. The
  tape's throw flies its full 44 ticks and misses, so the score stays 0 — what the geometry implies.
- **Launch response** at `delay_ms=108`: 0 ticks predicted, 15 without, 15 for the sensitivity control that
  presents authority while prediction runs (bound: ≥ 14 = 2 × 7 one-way ticks). 108 ms rather than m20.4's
  100: at exactly 6 ticks the impaired link's once-per-tick release adds a tick of jitter and the server
  stood in for the press in 4 of 6 runs.
- **Faults** (`dedicated --spawn-fault`, injected after session decoding, each counted): `refuse` → Rejected 1,
  cancel 1; `lose-one` → one copy dropped, recovered by redundancy 1; `lose-all` → retired without launch 1,
  no End, no resurrection; `duplicate` → 15 doubled checkpoints, 14 repeats ignored; `late-alive` (verdict
  held 15 ticks, client bound lowered to 5) → confirmed after expiry, alive 1, presentation resumed; `late-ended`
  (held 60 > the 45-tick life) → AcceptedEnded 1, stays absent. Every leg: live max 1, Launch exactly 1.
- **Controls that must fail:** `--spawn-debug-break no-ledger` plays Launch 88 times; `no-adopt` shows two live
  copies of one key. Both fail their gates in every run.

Before the wiring, an Opus adversarial review of the leaf (with mutation testing) measured two cases where
a server-accepted projectile ended up with its presentation cancelled for good — a reseed, or a guess
dropped on the client's own inference, cancelled the ledger key before any verdict. Fixed by the rule "only an
authoritative verdict cancels presentation"; the new tests kill the pre-fix code and four surviving mutants.

Not proven: Windows runs (the proofs are POSIX-gated until #351), more than one client, authenticated-state
injection (as ADR-0104's addendum), and faults selected by Throw specifically — the server picks "the first
command with any button pressed", because the engine does not know the game's buttons.

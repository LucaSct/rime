# ADR-0056: the software micro-triangle rasterizer resolves by atomic min of (depth, list index), and the fill rule is top-left in the y-down framebuffer

- Status: Accepted
- Date: 2026-09-30
- Refines: [ADR-0043](0043-virtualized-geometry-m18.md) gate 6 (hybrid software rasterization).
  Builds on [ADR-0044](0044-visibility-id-and-indirect-abi.md) (the 64-bit visibility ID).

## Context

ADR-0043 made the hybrid split mandatory: hardware rasterizes triangles that cover enough pixels,
a compute shader rasterizes sub-pixel ones, and the two must agree on depth, identity and
silhouette winners. The CPU side already existed in `micro_triangle.hpp`: an area classifier and an
allocation-free reference rasterizer (the oracle). M18.4 needed three decisions: how a compute
shader resolves the per-pixel winner, what to do on devices without 64-bit atomics, and what
"agree" means at a shared edge.

The textbook resolve (Nanite's) is a 64-bit image atomic min of `(depth << 32) | id`. It does not
fit here: ADR-0044's visibility ID is already 64 bits, so depth + ID is 96 bits.

## Decision

**1. Resolve by 64-bit atomic min of (depth key, list index), in a storage buffer.** Each pixel owns
one `uint64` in a transient buffer: the high half is an order-preserving key of the float depth
(the radix-sort sign flip; `-0.0` folded to `+0.0`, which the oracle's float compare treats as
equal), the low half is the triangle's index in this frame's software list. `atomicMin` is then
the depth test and a deterministic tie-break in one step: between equal depths the lower index —
the earlier triangle — wins, exactly the oracle's "a depth tie retains the existing pixel" for a
list processed in order. A fullscreen merge pass turns the index back into the 64-bit ID and writes
the hardware pass's own `RG32Uint`/`R32Uint`/`D32` targets. A storage buffer rather than an image
because the RHI has no `R64Uint` format and a buffer needs only `shaderBufferInt64Atomics`, not
`shaderImageInt64Atomics`.

**2. Hardware versus software is arbitrated by the depth test.** The merge loads the hardware
pass's depth (that pass now stores it), writes the software depth through `gl_FragDepth`, and
compares with `Less`. An exact tie keeps the hardware pixel: the hybrid frame is, by definition,
"every hardware triangle, then every software one". The proofs build their single-path reference
in that order.

**3. Without 64-bit atomics, two 32-bit passes, bit-identical by construction.** Pass one
`atomicMin`s the depth key; pass two re-rasterizes and, where its key equals the survivor,
`atomicMin`s the index. That is the same lexicographic minimum at twice the raster work and **no
precision cost** (the packed 32-bit alternative would have spent depth bits on the ID). Both
variants compile from one source, and the tests run both on every device and require identical
pixels and counters. Measured support for the single pass, via the new
`AdapterInfo::buffer_int64_atomics`: lavapipe (Mesa 26.2.3, LLVM 22) yes, RTX 3060 (NVIDIA 610.57)
yes, RADV (Mesa 26.2.1) yes. MoltenVK: not measured here.

**4. The fill rule is top-left in the y-down framebuffer, and the oracle is corrected to it.** The
oracle's `top_left` lambda owned *bottom/right* edges in the framebuffer it indexes (row 0 at the
top): watertight by itself, but mirrored. The boundary proof measured the hardware disagreeing with
it on 85 of 2304 pixels of one mesh (measured on the RTX 3060; lavapipe and RADV were run only
after the correction, where they agree with it on every pixel). The lambda now owns
left and flat-top edges, a CPU test pins the direction, and the shader translates the corrected
lambda verbatim. One pre-existing test case, whose sample sat exactly on a hypotenuse, silently
pinned the old rule and was moved inside.

**5. Bit-exactness is engineered, not hoped for.** Every float operation is written in the
oracle's order and marked `precise` (checked: all 28 add/sub/mul carry `NoContraction`); the
oracle's expressions are split into one-operation statements so clang's default
`-ffp-contract=on` cannot fuse them either. Vulkan guarantees correctly rounded add/sub/mul but
only 2.5 ulp for `OpFDiv`, so `1/area` is rebuilt by integer long division of the significand.
Falsified: with plain `1.0 / area`, NVIDIA and RADV mismatch the oracle by one ulp of depth
(lavapipe happens to divide exactly — a lavapipe-only proof would have missed this).

**6. The software path has an extent cap, and the router honours it.** One thread walks one
triangle's box, so a sub-pixel-*area* sliver 40 px long would stall its wave.
`route_micro_triangle` sends Software-classified triangles wider or taller than 16 px to hardware
(counted, not dropped); the shader counts anything oversized that still arrives. The cap also
bounds the area, which keeps `1/area` a normal float.

## Not yet (next bricks)

- **GPU-side projection and routing.** The pass consumes a CPU-projected, CPU-routed list. A frame
  path needs a compute pass that transforms a cluster's vertices, classifies, and appends to the
  software list (or per-cluster routing, as Nanite does), with the hardware pass skipping the
  software-routed triangles. Until then the hardware pass draws whole clusters.
- **Near-plane clipping** (ADR-0043 gate 6 names it): projected input assumes `w > 0`.
- **The measured micro-triangle gain** (gate 6's perf half) — no `docs/perf/` run in this brick.
- Denormal inputs and `-0.0` vertex depths are outside the parity claim (Vulkan may flush
  denormals; the key folds `-0.0`). Graph storage-*image* write→write hazards have the same
  no-barrier shape this brick fixed for buffers; not touched.

## Consequences

The visibility buffer stays one target with one ID format whichever rasterizer wrote a pixel; the
resolve pass and picking need no change. The render graph now barriers consecutive buffer writers,
which also closes a latent race for any future compute chain. The price is a `W×H×8`-byte transient
buffer, one clear dispatch and one fullscreen merge per frame, plus a second raster dispatch on
devices without 64-bit atomics.

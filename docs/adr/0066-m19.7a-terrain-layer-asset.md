# ADR-0066 (m19.7a): The TerrainLayer asset — a material, a packed albedo+height texture, world UVs

- Status: Accepted
- Date: 2026-10-05

## Context

Terrain blends up to four splat layers per texel (ADR-0063). Each palette slot names a cooked
**material**, and ADR-0064/0065 blend its base colour, metallic and roughness in difference form. The
transitions are a straight weighted cross-fade: where grass meets gravel, both fade into one smudge.
Real ground does not look like that. Gravel shows through grass along the low cracks first, and
grass stays on the high tufts. The standard technique is **height blending**: each layer carries a
height map, and at a transition the layer whose surface is locally *higher* wins more of the texel.

Luca chose real per-layer height maps over procedural noise, knowing it is three bricks:

1. **m19.7a (this ADR):** the asset contract, the cook and the reader. No GPU.
2. Terrain samples per-layer albedo+height textures at world-XZ UVs. Neutral textures must
   reproduce today's scalar render bit-exactly.
3. The height redistribution function and its proof.

Nothing in the engine carries a height map today. An outside consult (`gpt-6-astra`) and the
orchestrator agreed that the data belongs in a **terrain-specific** asset rather than in the general
material contract. They disagreed on two points, recorded below.

## Decision

### 1. A new asset kind, `TerrainLayer` (kind 10), and the general material stays untouched

`AssetKind::TerrainLayer = 10` (appended). `TerrainLayerAsset` is a fixed record like
`MaterialAsset`, 28 bytes on the wire:

| field | type | rule |
| --- | --- | --- |
| `material` | u64 AssetId | the cooked Material for base-colour factor, metallic, roughness; nonzero |
| `albedo_height` | u64 AssetId | a cooked RGBA8 texture, RGB = albedo, A = height; nonzero |
| `uv_scale` | 2 × f32 | metres per texture repeat along world X, Z; finite, > 0 |
| `height_contrast` | f32 | redistribution strength for brick 3; finite, ≥ 0; 0 = today's blend |

It has its own reflected schema hash (`terrain_layer_schema_hash()` = `0xFE7832A27003413C`) and
reader (`read_terrain_layer`, in the heightfield reader's shape). Every refusal is a typed
`AssetError` (new: `InvalidTerrainLayer`) and is tallied in the caller's `AssetRejectCounters`.

**Why not add the fields to `MaterialAsset`.** Every mesh reads it. Adding a height slot, a UV
scale and a contrast changes `material_schema_hash()`. Every material ever cooked would then be
refused as `SchemaMismatch` until re-cooked, all for three fields only terrain reads. The obvious
home for height, the base-colour alpha, already means opacity there (`AlphaMode`). So the layer
*references* a material for what the two share, and adds what only terrain needs.

### 2. No heightfield v3: a palette slot is dispatched on the referenced asset's kind

astra proposed a heightfield payload v3 whose palette references terrain layers, with v1/v2
decoding to neutral defaults. **The orchestrator overruled that.** Every cooked file's RMA1 header
already carries its `AssetKind`. So a v2 palette slot's AssetId may name either a `Material` (as
every v2 terrain does today) or a `TerrainLayer`. The code that builds the GPU terrain (the caller
of `TerrainPass::upload`, brick 2) reads the referenced file's header and dispatches on the kind.
Nothing in the heightfield format changes: no version bump, no schema-hash change. **A v2 file whose
palette references materials keeps loading and drawing unchanged**, and the existing
`terrain_splat.rhf` fixture and its test are untouched. The cost is that the heightfield alone no
longer says what its slots are: a tool that wants to know has to open the referenced file. That
was already true of a slot's *contents*.

### 3. One packed texture: RGB = albedo (sRGB), A = height (linear)

The layer's albedo and height are cooked into **one** RGBA8 texture with the existing
`RGBA8_SRGB` wire format. That is right for both halves. The Vulkan specification's definition of
`VK_FORMAT_R8G8B8A8_SRGB` ("Formats" chapter) applies the sRGB nonlinear encoding to R, G and B
only. Byte 3 is "an 8-bit A component" with no encoding. So the sampler linearises the albedo and
returns the height unchanged. One fetch serves both, and the engine needs no new texture format.

The cook (`texture.rs`) gains a cook-side `TextureUsage` (`Color = 0`, `TerrainAlbedoHeight = 1`,
append-only, not on the wire). For a terrain layer:

- **Colour mips stay gamma-correct**, exactly as for any sRGB texture.
- **Height mips are a plain box average.** The m16.6 alpha-coverage rescale is *not* applied:
  height is not coverage, and the rescale would inflate a layer's relief at distance.
- **Heights** come from 8- or 16-bit greyscale. 16-bit is rounded to nearest:
  `round(v / 257) = (2v + 257) / 514`. Ties are impossible, because `2v` is even and
  `257 · (2k + 1)` is odd. Truncation (`v >> 8`) would bias every layer down by about half a step,
  and the blend compares heights *across* layers.
- **Albedo** must be 8-bit RGB or RGBA, and **opaque**. A real alpha means the image was authored
  for something else, or already holds a height the cook would silently overwrite.
- Mismatched albedo and height sizes are **refused**, not resampled.
- **Uncompressed RGBA8 for now.** BC7 is mechanically available, but mode 6 shares endpoint error
  between colour and alpha. What that does to a height channel the blend *sharpens* has not been
  measured, so it waits for the brick that measures it.

The texture is a separate `.rtex` named by content id. That is how every texture reference in the
engine works, and it lets many tiles share one upload.

### 4. Cook input: `<name>.terrainlayer.toml`

```text
material = 0x1f2e3d4c5b6a7988   # cooked material AssetId, 0x hex, nonzero
albedo = "gravel_albedo.png"    # relative to the sidecar
height = "gravel_height.png"
uv_scale = [2.0, 2.0]
height_contrast = 8.0
```

The parser is hand-written and strict, in the heightfield sidecar's style. Every key is required,
and unknown or duplicate keys are errors. A `#` inside a quoted path is part of the path. The
command is `rime terrain-layer <name>.terrainlayer.toml --out <dir>`, which writes
`<name>_albedo_height.rtex` and `<name>.rtl`. Repeated runs produce byte-identical output. The
`terrain_layer.*` fixture pins those bytes in `cook_fixture.rs`, and `fixture_test.cpp` reads them
back exactly.

### 5. The blend brick 3 will implement — recorded now, revisable with evidence

Let `w_k` be the sampled splat weights and `h_k` the layer heights in `[0, 1]`. Let `c` be the
contrast and `h_max` the maximum of `h_k` over layers with `w_k > 0`. Then

```
g_k = exp2(c · (h_k − h_max))
b_k = w_k · g_k / Σ_j w_j · g_j
```

There is also an **explicit bypass**: when all active heights are equal, return the sampled `w_k`
unchanged. The renormalised form is mathematically the identity there, but it is not bit-exact,
and brick 2's neutral-texture anchor requires bit identity. The denominator is never zero: the
layer at `h_max` has `g = 1` and `w > 0`. `c = 0` gives `g ≡ 1`, i.e. today's blend.

**astra's alternative:** a gate `q_i = w_i · max(0, 1 − c_i (H − h_i) / d_i)` with `H = max h_i`
and a per-layer `d_i`, renormalised. **Not chosen**, because `H` ignores the painted weights. A
layer painted at 1 % that happens to be the highest pins `H`. Every layer more than `d_i / c_i`
below it then gates to exactly 0, and after renormalisation that 1 % layer can show at ~100 %,
overriding the painter. In the `exp2` form a layer's share still grows continuously with its painted weight, so
painting stays in control. A sharp contrast only *steepens* the transition. It never *moves* the
transition to wherever one stray texel is highest. One parameter (`c`) rather than two (`c_i`,
`d_i`) is deliberate: the second only reshapes a falloff the first already controls. It can be
appended later, with a schema bump, if brick 3 finds a case it cannot express.

## Consequences

- A heightfield's palette can now name richer layers without any change to the heightfield format
  or to the general material. Old cooks keep loading. `MaterialAsset`, `material_schema_hash()`
  and the heightfield's v1/v2 decoding are unchanged.
- Terrain gets a second asset to resolve per palette slot (layer → material + texture). Brick 2
  owns that resolution and its counted fallbacks.
- Brick 3 has a decided blend to implement and prove, with the reasoning against the alternative
  written down.

## Known limits

- **Not wired to the GPU.** Nothing loads a `TerrainLayer` at runtime yet. That is brick 2.
- **Not in the cook manifest.** `rime terrain-layer`, like `rime heightfield`, writes only its
  files: neither kind has a manifest name yet.
- **Uncompressed.** 4 bytes per texel until BC7 is measured on height.
- **8-bit height.** 256 levels over a layer's relief, which is ample for a blend weight but not a
  displacement map. A 16-bit height would need a second texture or a different format.
- **No per-layer normal map** yet. Height-blended albedo with a shared normal is the brick plan.

## Deferred

- Brick 2: per-layer texture sampling at world-XZ UVs, with the neutral-texture bit-identity anchor.
- Brick 3: the redistribution function above, its bypass, and its proof.
- BC7 for the packed texture, after measuring height error under mode 6.

## Addendum (2026-10-05, m19.7b — brick 2 landed: terrain samples the layer textures)

`TerrainPass` now samples one albedo+height texture per splat layer. Height *blending* is still
brick 3: the heights are read into a `vec4 h` and not used.

### What changed

- **The render-side `TerrainLayer`** gains `rhi::TextureHandle albedo_height` (invalid = no
  texture) and `float uv_scale[2]` (metres per repeat along world X and Z, default 1, 1).
  `height_contrast` is not added yet. It arrives in brick 3 with the code that reads it.
- **The builder uploads; the pass only binds.** The caller of `upload(asset, palette)` turns the
  layer's `albedo_height` AssetId into a GPU handle the same way every material texture is resolved:
  `GpuAssetBridge::texture_or_placeholder`, which creates the cooked `Rgba8Srgb` texture as
  `rhi::Format::RGBA8Srgb` with its cooked mip chain. The handle is **borrowed**. The builder keeps
  it alive while any tile uploaded with it is resident.
- **Four separate 2-D bindings (5–8), not a texture array.** An array forces every layer to one
  extent, one mip count and one allocation. Layer textures are independently cooked assets, shared
  between tiles and between terrains, and a 512² gravel next to a 2048² grass is the normal case.
  Resampling them into a shared array would be a per-terrain copy of data the bridge already holds.
  It would also add a second place where a layer's texels could drift from its cook. The cost is
  four descriptors instead of one. That is not a constraint at four layers.
- **One sampler for all four:** trilinear and `REPEAT`. Ground is seen minified at every distance,
  so it needs the cooked mips, and a layer tiles forever. There is no anisotropy yet (see Known
  limits).
- **The white fallback.** A layer with no texture binds a pass-owned 1×1 `RGBA8_SRGB` texel
  (255, 255, 255, 0). RGB 255 decodes to exactly 1.0, and any filter over all-1.0 texels returns
  1.0. So `base_color * tex.rgb` is `base_color` to the bit, and **every m19.4–m19.6 anchor holds
  unmodified, now running through the fallback**. A v1 tile binds the fallback in all four slots.
  Its flag keeps it off the textured path entirely.
- **Unused slots repeat layer 0** for the texture and the period too, exactly as they already did
  for colour, metallic and roughness. So an unused slot's `c_k − c_0` is exactly 0.
- **Colour:** `c_k = base_color_k * texture(layer_k, world.xz / uv_scale_k).rgb`. After that comes
  m19.4's difference-form blend, unchanged. Metallic and roughness stay scalar per layer.
- **World-XZ coordinates, not tile-local.** A tile-local coordinate restarts at each tile's
  origin. Unless every tile were a whole number of periods wide, the pattern would jump at every
  seam: a visible grid traced exactly where streaming cut the world. World XZ is one continuous
  function across tiles.
- **The splat UBO grows from 112 to 144 bytes.** Two `vec4 uv_scale[2]` are **appended** after
  m19.5's block, not interleaved, so the m19.6 proof's frozen m19.5 shader still reads the same
  buffer correctly. The `static_assert` and the GLSL block are updated together.
- **Refusals:** a `uv_scale` component that is zero, negative or non-finite moves both
  `splat_refused()` and `tiles_refused()`, in the same loop as the colour and material checks
  (all four slots).

### Proofs (`m19.7b:` in `tests/terrain_render/terrain_height_test.cpp`)

All measured on both an RTX 3060 and RADV (Raphael iGPU): 25/25 cases, 303100 assertions each.

- **Anchor (a).** A palette without textures is memcmp-identical to the same draw with explicit
  all-white textures whose A holds a height ramp. The weights are varied, the relief is non-flat
  and the sun is on.
- **Orientation and period (b).** A 4×2 texture is drawn on a pure layer-1 map and probed at texel
  centres over 8 × 16 periods. The test checks 1984 strict inequalities: red rises along +X, green
  rises along +Z, and both fall back exactly one period later. All 1984 hold. The same texels
  stored transposed, i.e. a U↔V swap, hold 0/1984.
- **Seam continuity (c).** Two adjacent tiles, with a 3 m period that does not divide the 32 m
  tile, are compared at `colour(x)` vs `colour(x + 3 m)` over 4988 pairs, 516 of which straddle
  the seam. **The bound is not one f16 ULP.** The first version asserted that and failed on the
  RTX 3060: 344 pairs, up to 20 ULP, every one with `u` straddling 2 or 4. The worst was exactly
  one 8-bit bilinear-weight step times the texture's 0.631 contrast. The texture unit quantises
  the weight to `subTexelPrecisionBits`, and `u` and `u + 1` in different binades round on
  different grids. The asserted bound is `2 · 2⁻⁴ · (decoded channel range) + 1 f16 ULP`. 2⁻⁴ is
  the weight precision the Vulkan spec *guarantees*, so the bound holds on any conformant device.
  Measured worst: 3.1 % (NV) and 3.2 % (RADV) of it. With every probe on a dyadic coordinate the
  pairs came out bit-identical, so the camera is deliberately offset 0.1 m to test the general
  case.
- **Refusals (d).** `uv_scale` of 0, −0, −2, NaN and +inf on either axis: 10 refusals, both
  counters. 1e-3 and 1e4 are accepted. A v1 asset ignores a NaN period, per the m19.4 contract.
- **Linear alpha (e).** m19.7a's cooked fixture is loaded through the engine's `GpuAssetBridge`
  and probed through a sampler configured like the pass's. The shader reads A = n/255 (worst error
  3.0e-8): A = 128 reads 0.502, not the sRGB-decoded 0.216. In the same fetch, R is sRGB-decoded
  (worst 1.2e-3 from the IEC curve). That is the witness that the texture really is sRGB, so the
  linear A is not just a UNORM upload. §3's inference from the Vulkan spec is now measured.
- **Falsified, each restored after:**
  - U↔V swapped in the shader turns (b) red (0/1984).
  - Tile-local `v_local` in place of world XZ turns (c) red (430 pairs, worst 7.6× the bound).
  - A fallback texel of 254 instead of 255 turns (a) red, along with the m19.4 equal-layers,
    pure-layer-0 and x-fastest anchors and the m19.5 equal-metallic anchor.

### Known limits (added)

- **No anisotropic filtering.** Grazing views blur toward the coarser mip. Anisotropy is a quality
  knob, and leaving it off keeps every proof independent of a per-device footprint the spec does
  not pin down.
- **World-coordinate precision.** An f32 world X resolves about 1 mm at 10 km. That is far below a
  texel, but (c) shows the texture unit's own coordinate precision also falls with |u|.
  World-origin rebasing will answer both when worlds get that large.
- **No builder in the engine yet.** The kind dispatch of §2 (read the slot's header, then resolve
  a `TerrainLayer` to its material and texture) is still the caller's. The tests build palettes
  directly. A terrain builder that owns that resolution, with counted fallbacks, is still to be
  written. This brick delivered only the pass half of "brick 2 owns that resolution".

## Addendum (2026-10-06, m19.7c — brick 3 landed: the height blend)

`terrain.frag` now redistributes the painted splat weights by the layers' heights, as §5 decided.
This closes the three-brick plan in the Context.

### The blend as built

- **The render-side `TerrainLayer`** gains `float height_contrast = 0.0f`. It must be finite and
  ≥ 0. Anything else moves both `splat_refused()` and `tiles_refused()`, in the same loop as every
  other per-layer check. The four contrasts ride in the splat UBO as one more **appended** `vec4`
  (144 → 160 bytes), so the frozen m19.5 reference shader still reads the buffer.
- **One function, `height_blend(w, h, c)`, in `terrain.frag`.** With `w` the sampled weights, `h`
  the four texture alphas and `c` the contrasts:
  - the *painted* layers are those with `w_k > 0`, and `h_max` is taken over them only;
  - **bypass:** if every painted layer has the same `h`, or every painted layer has `c_k = 0`, it
    returns `w` itself;
  - otherwise `g_k = exp2(c_k · (h_k − h_max))` and `b_k = w_k g_k / Σ_j w_j g_j`.
  `b_1..b_3` then feed the m19.4 difference-form blend for colour, metallic and roughness, where
  `w_1..w_3` used to. `b_0` is implied, as `w_0` was.
- **The contrast is per layer** (`c_k`), where §5 wrote a single `c`. The asset already carries one
  per layer; the unit is "halvings per unit of height below the highest painted layer".
- **One guard beyond §5:** the exponent is `c_k · min(h_k − h_max, 0)`. For a painted layer the
  `min` changes nothing, because `h_k ≤ h_max` by construction. For an *unpainted* layer taller
  than `h_max`, a large contrast would overflow `exp2` to +inf, and `0 · inf` is NaN, which would
  poison the sum. With the guard its `g` stays ≤ 1 and its term is an exact 0.
- **Nothing on the CPU mirrors the function.** Every proof draws through `TerrainPass`.

### What the bypass does, and a correction to how it is tested

§5 said the bypass is needed because `w / Σw` is not bit-exact. That is true, but the difference is
one **f32** ULP and the frame is **f16**, about 8000 times coarser. **Measured: with the bypass
deleted outright, all 25 earlier cases still pass on both GPUs.** An ordinary scene cannot see it.

So the anchor uses a scene built to amplify one ULP. Layer 1 is painted at 127/255 everywhere, with
`c_0 = −(127/255)·K` and `c_1 = c_0 + K`, `K ≈ 2²⁰`. The blended colour is then
`K · (b_1 − 127/255)`: a cancellation whose result consists entirely of the rounding in `b_1`.
The claims remain bit identities between draws of one program. They have two legs, because
"contrast ≠ 0 equals contrast 0" alone **cannot** detect a missing bypass: both draws would then
take the same renormalised path and still agree.

1. Equal heights with contrasts (8, 3, 0.5, 20) are memcmp-identical to contrast 0.
2. Two weight maps that agree on `w_1` and split the remaining 128/255 differently among three
   identical layers are memcmp-identical. That is m19.7b's blend stated as a property: it never
   read `w_0`. The renormalised form divides by `Σw`, whose rounding depends on the split.

Separately measured: the m19.7b textured anchor scene hashes byte-identically under m19.7b's
shader and this one, on both GPUs. That is two programs, so it is an observation on these drivers,
not a guarantee.

### Proofs (`m19.7c:` in `tests/terrain_render/terrain_height_test.cpp`)

Measured on an RTX 3060 and on RADV (Raphael iGPU): 30/30 cases, 426630 assertions each. All
scenes are a flat tile, sun off, ambient 1.

- **(a) Equal heights.** The two legs above, plus two witnesses: every pixel is drawn, and raising
  one layer's height in the same scene changes the picture.
- **(b) Redistribution happens.** A uniform 128/127 map between a red-orange and a cyan layer.
  Layer 1's height is 1 over one half of the tile and 0 over the other, layer 0's is 128/255,
  contrast 4. On every channel of every probed pixel the render lies strictly between the plain
  50/50 render and layer 1's pure render in the high half, and strictly between the 50/50 and
  layer 0's in the low half: 28800/28800. With the height map's halves swapped: 0/28800. Read back
  off the red channel, layer 1's share of the 0.498 texel is **0.798** (high) and **0.198** (low)
  on both GPUs. The formula predicts 0.798 and 0.198.
- **(c) The painter is respected.** Layers 0, 1 and 3 are painted with varied maps, varied height
  maps and unequal contrasts (2, 6, 3). Layer 2's weight byte is 0 in every texel. Three draws are
  memcmp-identical: layer 2 at height 255, magenta, base colour (50, 0, 50), metallic, contrast 30;
  layer 2 at height 0, green, another colour, contrast 0; layer 2 untextured. It is exact because
  a linear filter over zeros returns exactly 0, so layer 2 is outside `h_max` and the bypass test,
  adds `0 · g = 0` to the sum, gets `b_2 = 0`, and enters the blend only as `0 · (c_2 − c_0)`.
  Witnesses: dropping the contrasts changes the picture, and once layer 2 is painted the two
  variants differ.
- **(d) Monotone in painted weight.** At fixed heights and contrast 6, nine uniform maps with
  `w_1` = 0, 32, …, 224, 255. Every step moves every channel strictly toward layer 1, with layer 1
  both the lower layer and the higher one: 5400/5400 strict steps in each arrangement.
- **(e) Refusals.** −1, −1e-6, NaN, +inf and −inf, in each of the four slots: 20 refusals, both
  counters. 0 and 1e6 are accepted. A v1 asset ignores a NaN contrast.
- **Falsified on both GPUs, each restored after:**
  - bypass deleted → (a) leg 2 red; leg 1 and every earlier case stay green, as explained above;
  - only the equal-heights clause deleted → (a) leg 1 red;
  - `h_max` taken over all four layers → (c) red, and nothing else. This needs the unequal
    contrasts: with one common contrast the shift cancels in the renormalisation;
  - the `w_k` factor dropped → (c) red, and (b) and (d) with it;
  - `exp2(−c · …)`, i.e. high and low swapped → (b) red, and (d)'s height witness.

### Known limits (added)

- **No triplanar mapping.** Layer textures are projected along world Y. On a steep slope both the
  albedo and the height stretch, so the blend follows a smeared height there.
- **No per-layer normal map.** The redistributed transition has a height-shaped *outline* but the
  shading is still the triangle's facet normal.
- **8-bit height.** 256 levels. At contrast `c` one level changes `g` by a factor `2^(c/255)`,
  which is 2 % at `c = 8`. That is invisible, but a contrast in the hundreds would band.
- **The bypass is a float equality.** Two layers whose constant heights are equal are bypassed.
  Heights that differ by one 8-bit level are not, and go through the renormalised form. The two
  results differ by an f32 ULP, far below what an f16 frame shows, so there is no visible seam.
- **The engine-side builder is still missing** (m19.8a). Nothing copies the cooked
  `TerrainLayerAsset::height_contrast` into a render-side layer yet. The tests build palettes
  directly.
- **Cost not measured.** The blend adds one `exp2` over a vec4 and one divide per pixel of a tile
  with height data, and nothing on the bypass path beyond the loop. No frame-time measurement was
  taken.

# ADR-0108: m20.8 — several remote clients on `dedicated`, around an engine-owned seat roster

- Status: Proposed (2026-10-26, overnight). The order is the owner's (2026-10-25: interaction group first, then
  multi-client; default client cap **16**); the contract below is a proposal for the owner to accept. Only the
  pure leaf (m20.8a) is built before acceptance, and it changes no wire format and no game contract.
- Date: 2026-10-26
- Extends: ADR-0103, ADR-0104, ADR-0105, ADR-0106. Design source: the Opus 5.5 scope consult
  `/home/next/reports/rime-oct25-m20.6-scope/out.md` (path:line evidence there; summarised here).

## Context

Everything between the socket and the game is single-seat: one `admitted` session, one `InputSchedule`, one owner,
one `membership_epoch` (`engine/app/src/network_input.cpp`), one `TickContext::input`, one `owned_player(World&)`,
and hello-game keeps its player in a world singleton. `ServerReplicator` is already per client. ROADMAP M20 names
"host a multiplayer session"; that needs N seats.

## Decision (proposed)

1. **An engine-owned seat roster.** A seat is a `PlayerSlot { u16 index; u16 generation; }`: a dense index for O(1)
   per-seat arrays, and a generation so a stale slot addresses nothing (the `SessionId` rule). Not a `SessionId`
   (the host's own player has none) and not an entity (a respawned player is a new entity in the same seat). The
   lowest free index is reused; every release bumps that index's generation.
2. **The game contract** (m20.8b): `TickContext::players` — one `PlayerInput { slot, actions, command, refuse_spawn }`
   per seated player, in index order; `on_player_joined(slot)` (the game spawns the body; `false` refuses, counted)
   and `on_player_left(slot)` at the START of a tick, before inputs; `owned_player(World&, PlayerSlot)`;
   `SpawnReport::owner`; `GameDefinition::max_players = 1`. **With `max_players == 1` everything is bit-identical
   to m20.3–m20.7** (`ctx.input == players[0].actions`) — the gate that keeps the contract from leaking into every
   game.
3. **Per seat on the server:** schedule, owner checkpoint (own player, own spawns, own group state), input result,
   membership epoch, retained outcomes (capped at 32). Other players reach a client only through the replicator.
4. **Seat on the wire:** hello reply v3 adds `seat:u16 gen:u16` under input codec 3; a server with
   `max_players > 1` refuses older clients as `version`. A replicated `PlayerOwner { index, generation }` lets a
   client find its own player without a game-specific lookup.
5. **Admission (unauthenticated LAN):** `--max-clients N` (default `min(16, max_players)`; the CLI may lower, never
   raise); transport sessions N + 1 (one to deliver `full`); a per-endpoint poll cap inside a global budget so one
   flooder cannot starve the rest; one seat per source endpoint; a join rate limit. Every refusal counted.
6. **The proof** (m20.8c), `hello_game_multi_client`: three real clients with different tapes and impairments.
   Digest agreement is necessary and NOT sufficient — every client mirrors the same authority, so a misrouted
   server is green on digests. The done-criterion is therefore attribution: the per-seat applied trace replays to
   the digest and swapping two seats' traces changes it; a `--seat-debug-break swap` control must fail the
   response/snap gates; isolation under one client's blackout; spawn outcomes reach only their owner; churn
   reuses a seat with generation + 1; floods are capped per peer (with a control that must fail).

## Bricks

m20.8a, the pure `SeatTable` leaf (built overnight, unwired); m20.8b, the game contract and hello-game with N
players (after acceptance); m20.8c, the N-process proof; then `host` as "dedicated plus one seat fed by the local
mapper".

## Consequences

- The biggest risk is silent cross-seat aliasing — single-instance state half-converted to per-seat — and digest
  agreement cannot see it; the attribution gates exist for it.
- With the adaptive buffer (ADR-0107) each seat's schedule stalls and drains on its own; nothing is shared.

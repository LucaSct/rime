# ADR-0062 (m19.3): The terrain heightfield draws from the integers physics collides with

- Status: Accepted (number provisional — 0055..0061 are held by open PRs; renumbered at merge)
- Date: 2026-10-04

## Context

M19.1 (ADR-0060) cooked the terrain heightfield — a regular grid of u16 samples with a scale, an
offset and the cell triangulation in the header — and gave `rime::physics` a shape that rays, boxes
and capsules collide against. Nothing drew it. m19.3 is the draw.

A terrain draw is not an interesting rendering problem on its own: it is a grid of triangles. What
makes it worth an ADR is the failure it is easy to ship. Every engine with terrain in it has at
some point drawn ground a few centimetres away from the ground it simulated, and the symptom is
unmistakable from the player's seat — a ball resting in mid-air, or a character's feet sunk into a
slope. The cause is always the same: **two representations of one surface**, each derived correctly
from different numbers, or from the same numbers at different times.

ADR-0060 §1 already chose the mechanism that prevents it, in advance:

> the renderer can upload the samples as `R16_UNORM` and apply the same scale/offset, so the
> surface drawn and the surface collided with come from the same integers.

This ADR is where that sentence is actually built, and — more importantly — where it is
**measured**. The forces specific to the draw:

- **The heights are integers, and they must stay integers until the GPU.** The obvious
  implementation (walk the samples on the CPU, build a float vertex buffer) is also the one that
  creates the second representation. Any CPU-side dequantisation is a conversion that can be
  rebuilt from stale data, rounded differently, or simply written twice.
- **A non-planar grid cell has two surfaces, not one.** Four corners that are not coplanar describe
  a different surface under each diagonal. If the renderer splits a cell one way and physics the
  other, *every sample still agrees* and the surfaces still differ — by the cell's non-planarity.
  This is the failure mode that a "do the heights match?" test over samples alone cannot see.
- **A proof of agreement must be able to fail.** Comparing two numbers that agree to within a
  margin says nothing unless the margin is small enough to reject a wrong surface. The margin
  therefore has to be *derived* from the quantisation, not chosen for comfort, and the proof has to
  demonstrate what it rejects.
- **Terrain is not yet part of a scene.** There is no terrain component, no terrain in the ECS, no
  streaming. A pass that assumed any of those would have to be rewritten when they arrive.

## Decision

### 1. `rhi::Format::R16Unorm`, and the samples reach the GPU as a `memcpy`

One new RHI format (`engine/rhi/include/rime/rhi/types.hpp`, mapped to `VK_FORMAT_R16_UNORM` in the
Vulkan backend — the only place that names a Vulkan enum). `TerrainPass::upload` copies
`HeightfieldAsset::samples` into the texture directly: the asset's layout is row-major with x
fastest, which is exactly a 2-D texture upload's walk, and R16_UNORM's storage *is* the `u16`. **No
float touches a height anywhere on the path to the GPU**, so there is no conversion to get wrong —
a stronger guarantee than any amount of careful conversion code.

Sampled and transfer support for R16_UNORM is Vulkan-spec-mandatory, so no device query is needed.

### 2. The vertex stage is a vertex PULLER; the draw binds no vertex buffer

`engine/render/shaders/terrain.vert`: `gl_VertexIndex` is decomposed into grid coordinates
`(i, j) = (index % columns, index / columns)`, the sample is read with `texelFetch` at those integer
coordinates, and the height is

```
height = height_offset + height_scale * (texelFetch(...).r * 65535.0)
```

— character for character the expression `HeightfieldShape::h()` evaluates on the CPU
(`engine/physics/src/heightfield.hpp`). `texelFetch`, not a filtered `texture()` call: a grid vertex
*is* a sample, so fetching it by index is exact, cannot be perturbed by a sampler misconfiguration,
and is what lets the proof's margin be derived from the unorm round trip alone.

There is consequently no vertex buffer and no vertex layout. That is the point: there is no second
copy of the terrain to keep in sync, because there is no second copy.

### 3. The index buffer carries ADR-0060's triangulation, read from the asset's own header

Cell `(ci, cj)` is split along its `v00–v11` diagonal, triangle A `(v00, v10, v11)` then B
`(v00, v11, v01)` — the same order `heightfield_detail::triangle_vertices` builds. `upload()`
**refuses** a `HeightfieldTriangulation` value this build does not know (the reader's "reject values
you do not recognise" posture, applied at the GPU boundary) rather than drawing it with the only
diagonal it has.

### 4. The shading normal is the drawn triangle's own plane normal

`terrain.frag` recovers it as `normalize(cross(dFdx(v_world), dFdy(v_world)))`, flipped to point up.
Over a triangle, world position is affine in screen position, so those two derivatives lie in the
triangle's plane and their cross product is that plane's normal — exactly, not approximately.

The tempting alternative is a central-difference normal from the four neighbouring samples. It
looks better, and it describes a *smooth* surface that nothing collides with: ADR-0060 §2's contact
routines force the triangle normal ("forcing the triangle normal is the point"), so a box sliding
over this terrain slides on facets. Shading it as facets keeps the picture and the simulation
telling the same story, and costs no extra texture reads.

The rest of the shading is deliberately minimal — one directional light, Lambert with its `1/π`,
plus an ambient term, one flat albedo, into the HDR target. Splat blending is a later M19 brick and
this shader is not where that gets pre-empted.

### 5. One pass, owned like `FxParticlePass`, gated structurally

`TerrainPass` is a standalone pass object the caller composes into its frame — not something
`SceneRenderer` reaches into. Nothing in `rime_render` includes `terrain_pass.hpp`, so the
modularity guardrail is satisfied structurally: **deleting the four files and their two CMake lines
leaves the whole engine and test suite building** (measured 2026-10-04 by doing exactly that).

`add()` with a tile id this pass does not hold declares **no pass at all** — no pipeline bind, no
barrier, no attachment load — so a frame without terrain is byte-identical to a build without this
file in it. ADR-0032 §11's rule: a pass that ran and drew nothing would be *almost* that, and a
regression bridge cannot be built on almost.

Refusals and draws are both counted (`tiles_refused()`, `tiles_drawn()`), because a refused tile and
a tile nobody handed over produce the same empty frame.

### 6. The push block is 128 bytes, public, and built by one function

`TerrainPush` (view-projection, placement, grid, sun, surface) is exactly the 128 bytes every Vulkan
implementation guarantees, `static_assert`ed against that size. It is **public**, and so is
`terrain_push()`, because the proof builds a second pipeline around this pass's own vertex stage:
handing it the engine's constant-block builder is what keeps the two from assembling differently
shaped blocks. `columns` travels as a float in the block — exact below 2²⁴, and ADR-0060 caps an
axis at 32768 — which buys the 16 bytes the fragment stage's light needs.

## The proof

`tests/terrain_render/terrain_height_test.cpp`, its own test target because it is the only test in
the tree needing `rime::render` **and** `rime::physics` **and** a device. The glue that turns one
`std::vector<std::uint16_t>` into both a `HeightfieldAsset` and a `HeightfieldDesc` lives in the
test, deliberately: `rime::physics` does not depend on `engine/assets` (ADR-0060 §2) and never will,
so nothing in the engine performs that conversion — and "one set of integers, two consumers" is
precisely the claim.

Structural, in the M5.6/M6.4 style, no golden images:

- **The agreement.** At 36 probe positions spread over a 32 m tile (ADR-0062's bar is ≥ 16), the
  world height the engine's vertex stage reconstructs on the GPU is compared with the world height
  a `rime::physics` raycast lands on. The GPU height is transported losslessly:
  `floatBitsToUint` into an `R32Uint` target, because RGBA16Float's step at 20 m is ~16 mm and would
  make the test measure the target instead of the terrain.
- **The margin is derived**, in a comment at `kMargin`: the R16_UNORM round trip costs ≈ 1.9 × 10⁻⁶ m
  (≈ 6 × 10⁻³ of a quantisation step), the f32 dequantisation on both sides ≈ 5 × 10⁻⁶ m, and
  interpolation plus the ray's own arithmetic ≈ 5 × 10⁻⁵ m, which dominates. Sum ≈ 6 × 10⁻⁵ m; the
  margin is **1 mm**, ~16× that bound to leave room for unspecified barycentric precision, and still
  only 3.3 quantisation steps of this tile.
- **The margin is shown to discriminate.** The same comparison is run against the *opposite* cell
  diagonal and must be rejected: measured, a flipped diagonal is rejected at **36 / 36** probes, by
  up to **96.8 mm** — ~97× the margin. Counted per probe rather than reduced to one worst case,
  because the two diagonals genuinely coincide along the edge they share, so a probe near `u == v`
  cannot distinguish them and is not asked to.
- **The pass is proven to draw**, not merely to be declarable: a second case drives
  `TerrainPass::add` into an HDR frame and checks the measured radiance against the analytic Lambert
  value computed from the CPU's own faceted triangle normals. That check fails for a smooth
  (central-difference) normal, for a dropped `1/π`, and for a light aimed the wrong way.
- **The gate and the refusals** get their own cases: an unknown tile declares zero passes, and each
  of seven malformed assets is refused and tallied.

Measured on 2026-10-04, on two independent drivers (NVIDIA proprietary and Mesa RADV), with Vulkan
validation on and silent:

| quantity | measured |
|---|---|
| worst \|GPU height − physics raycast\| over 36 probes | **9.5 × 10⁻⁶ m** (margin 1 × 10⁻³ m) |
| height swept across the probes | 10.7 m |
| flipped-diagonal surface rejected at | 36 / 36 probes, by up to 0.0968 m |
| worst relative radiance error vs. analytic Lambert | 9.0 × 10⁻⁴ |

### What the proof does NOT cover

Recorded here so none of it is rediscovered as a surprise:

- **Lavapipe was not exercised locally.** This workstation has no lavapipe ICD installed (only
  `nvidia_icd.json` and `radeon_icd.json`), so the two drivers above are what the numbers come from.
  CI's Linux legs run on lavapipe and are the first place the software rasteriser sees this test.
- **A posed tile is not drawn.** The pass places a tile by translation only, because
  `HeightfieldAsset` carries an `origin` and no rotation. The *physics* store accepts a yawed tile;
  nothing proves the two agree under a yaw, because the renderer cannot express one.
- **The probes are interior.** Every probe sits strictly inside the tile and strictly inside one
  triangle (the 128² target over a 32 m tile puts pixel centres on a 0.25 m lattice offset by
  0.125 m, so none can land on a cell boundary). Behaviour at the tile's **edges and corners** — and
  how two adjacent tiles meet — is untested, and tile seams are exactly where a streaming brick will
  need a proof of its own.
- **One tile, one grid shape, one spacing.** 33 × 33 samples, 1 m square cells, a 20 m height range.
  Non-square cells, anisotropic spacing, very large or very small `height_scale`, and a tile whose
  samples reach the format's 0 / 65535 ends are all untested (the fixture asserts it does *not*
  clamp, so the clamping regime is explicitly out of scope).
- **The shading check reads 36 pixels, not a picture.** Nothing proves the whole tile is covered,
  that triangles are not missing in some region, or that the depth test orders terrain correctly
  against other geometry — no other geometry is in the frame.
- **No performance claim whatsoever.** A tile is drawn at full sample density every frame, with one
  draw call and no culling; nothing has been measured and ADR-0035 §2c's rule is that an
  optimisation arrives with its measurement.
- **The `R16Unorm` format is proven only through this one path.** Nothing tests it as a render
  target, a storage image, or with filtering turned on — and `shaderStorageImageExtendedFormats`
  would be required for the storage case.

## Consequences

- Terrain can be cooked (M19.1), collided with (M19.1) and now **drawn**, from one set of integers,
  with the agreement measured rather than asserted. The later M19 bricks — splat blending,
  streaming, LOD — all build on this same texture and this same vertex stage.
- The engine gains exactly one RHI format and four files. `rime_render` grows no new dependency:
  `rime::assets` was already a PUBLIC link (the one allowed assets↔render edge, ADR-0025).
- **Deferred, and why each is deferred rather than forgotten:**
  - **LOD / clipmap / tessellation.** A tile is drawn at full density. The cost is bounded and
    measurable; the fix needs a measurement first.
  - **Streaming.** `upload()` is one-shot and a tile stays resident until the pass dies. ADR-0060
    §2's scaling answer is *many tiles*, and the brick that introduces them owns their residency.
  - **An index buffer per tile.** 6·(columns−1)·(rows−1) `u32`s, so `kMaxTileSamplesPerAxis` is
    capped at 1024 (≈ 25 MB of indices at the cap) and anything larger is refused and counted. Tiles
    of identical dimensions could share one buffer, and a GPU-side grid needs none at all; neither
    is worth doing before a scene has more than one tile in it.
  - **Terrain in the ECS.** No component, no extraction, no `SceneRenderer` wiring — so a sun comes
    from the caller rather than from the scene's own light. That edge belongs to whichever brick
    puts terrain in a `.rscene`.
  - **Splat blending, holes, decals, per-cell best-fit diagonals.** The first is a named M19 brick;
    the others the cooked format cannot express either, so they are format changes before they are
    render changes.
- A tile's heights are uploaded once and never invalidated. When destruction or authoring edits a
  heightfield in place, something will have to re-upload the changed region — there is no dirty
  tracking here, and nothing counts a stale tile, because nothing can yet produce one.

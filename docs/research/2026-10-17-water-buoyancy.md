# Water and buoyancy: evidence for a separate track

Research checked 2026-10-17. This is a design brief, not an implementation or a performance estimate. Rime's [ADR-0042](../../docs/adr/0042-fluids-track-reopened.md) orders `fx1b → fl1a → fx1c` after M18, with visible water later as `fl1b`. That ordering remains the approved plan unless the owner revises it. The checkout has a terrain heightfield shape API in `PhysicsWorld::register_heightfield`, but that is ground collision, not a water volume. The Block's current puddles and pond are static rendered meshes in `play_environment.cpp`; no fluid solver or buoyancy should be inferred from them. `PhysicsWorld::apply_impulse(id, J, point)` provides an external force seam, and `Device::wait_and_borrow` protects a completed command buffer's lifetime. Its documented purpose is timestamp readback; it does **not** itself specify a water buffer staging/readback protocol.

## Six sources worth inspecting

1. **Chentanez and Müller, “Real-time Simulation of Large Bodies of Water with Small Scale Details” (2010)** — [author-hosted paper](https://matthias-research.github.io/pages/publications/hfFluid.pdf). Professional two-way heightfield reference. It orders grid step, solid step, force integration, solid displacement into water, then optional particle detail. The staggered grid stores depth at centers and velocities on faces. Use the coupling and conservation questions as design guidance. Treat paper algorithms as conceptual inspiration; the paper is not a code license. Its splashes and screen-space rendering are later seams, and explicit integration requires stability limits.

2. **Matthias Müller, Ten Minute Physics 20 and 18** — [heightfield tutorial and source index](https://matthias-research.github.io/pages/tenMinutePhysics/index.html), [heightfield source](https://github.com/matthias-research/pages/blob/master/tenMinutePhysics/20-heightFieldWater.html), [FLIP source](https://github.com/matthias-research/pages/blob/master/tenMinutePhysics/18-flip.html). Tutorial 20's `simulateCoupling` computes sphere-column submerged depth, applies buoyancy, and deposits changed body displacement into the surface; this is a compact prototype for a single buoy at rest and perturbation test. Its wave-height update is a teaching model, not a full mass-and-horizontal-momentum-conserving shallow-water solver. I found no license notice in the tutorial-20 source file, so **study it but do not copy its code** without a separate grant. Tutorial 18's source contains an MIT notice, subject to preserving its notice if copied; its particle-grid transfers belong to a later FLIP experiment, not `fl1a`.

3. **Kiril Boychev, `fvm_shallow_water`** — [solver.cpp](https://github.com/KBoychev/fvm_shallow_water/blob/master/solver/solver.cpp), [method description](https://github.com/KBoychev/fvm_shallow_water), [MIT license](https://raw.githubusercontent.com/KBoychev/fvm_shallow_water/master/LICENSE). Concrete conservative variables `[h,hu,hv]`, face fluxes and dam-break examples can inform the CPU oracle and a deliberately leaky negative control. MIT permits reuse with copyright and permission notice. The code uses unstructured finite volumes, Eigen and OpenMP, so direct integration would pull in machinery a bounded 256² regular basin does not need. Inspect exact solver/auxiliary-file provenance before copying any fragment.

4. **Stephen Thompson, Shallow Water Demo** — [developer's technical post](https://www.solarflare.org.uk/shallow_water), [three-pass `kp07.hlsl`](https://github.com/sdthompson1/shallow-water-demo/blob/main/shaders/kp07.hlsl), [repository legal terms](https://github.com/sdthompson1/shallow-water-demo#copyright--legal-information). A real GPU shallow-water implementation of a positivity-preserving, well-balanced scheme, with shoreline and ghost-cell ideas to examine when porting the CPU oracle to compute. The author reports resolution cost and spiky artifacts, so do not treat it as a measured Rime budget. The demo code is GPLv3; use as conceptual reference only for this engine unless its licensing is deliberately accepted and reviewed. Its DirectX/HLSL pass layout is not Rime's render architecture.

5. **Epic, Unreal Water buoyancy** — [current component documentation](https://dev.epicgames.com/documentation/unreal-engine/water-buoyancy-component-in-unreal-engine), [API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/Water/UBuoyancyComponent). Professional real-time game example: a small set of spherical pontoons approximates submerged volume; the API separates water height/velocity sampling, force, drag and asynchronous physics inputs. Use that *interface split* to scope Rime's first buoy and cost cap. Its documented pontoon model is a low-cost approximation, not a conservative two-way water solver. Epic's API page supplies no permission to transplant Unreal code.

6. **Jeschke and Wojtan, SIGGRAPH 2023** — [NVIDIA research page](https://research.nvidia.com/labs/prl/shallow-water-simulation/). Current professional heightfield research separates bulk shallow-water flow from dispersive surface waves, then recombines velocity. It is a useful later quality direction if a basin wake looks too slow or nondispersive; no source code or reuse license was verified. It adds a second wave solver and should not enter the first coupling seam.

A separate individual developer example, [Gabriele Giuseppini's Floating Sandbox](https://github.com/GabrieleGiuseppini/Floating-Sandbox), shows modified shallow-water surface feedback from bodies. The actual source is under `Sources/Simulation/Physics/OceanSurface.cpp`. Its [license text](https://raw.githubusercontent.com/GabrieleGiuseppini/Floating-Sandbox/master/license.txt) allows learning but explicitly forbids distributing built deliverables or assets. Because that text is more restrictive than a conventional permissive software license, it is a **conceptual reference only**, not a candidate for copied code. It is also a 2D mass-spring ship simulation, so its body representation is a poor direct fit for Rime's 3D rigid bodies.

## First seam and authority rule

A small `engine/fluids` module should own `WaterGrid` (bed elevation, depth, face momentum, boundaries, tick), `WaterBodyProxy` (stable body ID, sphere or capped proxy, transform and velocity), and `WaterStepResult` (next grid state, sorted `BuoyancyImpulse{id, impulse, point}`, displacement accounting, checksums). The consumer gathers bodies in stable order, gives the module a fixed-step snapshot, then applies impulses through the existing public physics API. Begin with one sphere or a bounded pontoon set; prove positive depth, mass balance, dry-cell behavior, a floating rest position, decay after a drop, and equal-and-opposite disturbance accounting. A visual surface samples the validated snapshot in a separate brick. `HeightfieldDesc` is a *terrain* collider interface and should not be relabeled as water collision.

For authoritative multiplayer, forces affecting body state must derive from a canonical input and deterministic update, or come from the authoritative server over the wire. A GPU readback that is one tick old has a defined lag, **not** automatic bit-exact equality across GPUs or peers. The ADR's phrase “deterministic-input by construction” is therefore an unproved assertion for GPU-derived forces. Start the gameplay-force path with a CPU oracle or server-authored quantized impulses; keep any GPU surface cosmetic until cross-device force agreement, ordering, and replay have passed. Use `destruction_net::shared_state_hash` only as a convergence witness, with an explicit water/body-state witness as well.

## Separate milestone gates

1. **FL proof, no GPU dependency:** fixed 256² or smaller bounded basin; documented CFL/substep rule and wet/dry policy; still-water over uneven bed, dam-break and leaky-control tests; 10,000-step mass drift and energy/decay bounds specified *before* capture. This establishes a numerical oracle, not visible water.
2. **Two-way buoyancy seam:** one sphere then bounded pontoons; per-body impulses through `PhysicsWorld::apply_impulse`; static float, sinking heavy body, drop/re-bob, displacement and impulse accounting; canonical body order; headless replay and server/client state convergence. Distinguish wave feedback from genuine two-way momentum conservation in results.
3. **GPU compute and readback:** CPU/GPU field comparison with an explicit tolerance; staged readback lifetime, one-tick timestamp and failure handling; cross-device authority test. If gameplay forces cannot be made deterministic, retain server CPU authority and use GPU only for visuals. Report CPU/GPU time and readback stalls against the current gated budgets rather than the ADR's unmeasured estimates.
4. **Visible basin, separate `fl1b`:** grid surface and shoreline, reflected/refraction response appropriate to the existing pond, captured image witnesses, frame cost and stable body/water alignment. Later splash particles are a visual effect, not solver proof.
5. **Optional full-fluid research:** only after the approved trigger and measured headroom, prototype PIC/FLIP/APIC for pouring, overturning and vertical structure. PBF/SPH and smoke/fire field coupling are distinct investigations; none is necessary to validate the initial heightfield seam.

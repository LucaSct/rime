# Rime smoke, destruction smoke, and fire lighting: research and initial seams

Research checked 2026-10-17. Read-only review of Rime; no repository edits, builds, or copied third-party source.

## Recommendation and boundaries

Treat **general smoke**, **destruction smoke**, and **fire lighting/smoke** as separate, observable milestones. Reuse a small *emission description* and the existing FX draw/lighting bridges, rather than assert that all three need one fluid solver. Smoke particles carry position, age, velocity, size, and family; density volumes carry at least density, velocity, and often temperature/fuel on a grid. A divergence-free pressure projection acts on the velocity field, not on Rime's existing independent particles. Fire-driven light can be a short-lived lighting input while flame propagation and damage remain outside this visual track. Water's heightfield and two-way physics coupling remain the distinct `fl1a` track from ADR-0042; a generic “fluid” base would create dependency and frame costs before a shared requirement exists.

**Authoritative boundary:** `destruction::DestructionEvent` and gameplay weapon/ignition state are the causes. Locally simulated smoke and light are cosmetic effects, excluded from replicated state as ADR-0042 specifies. If smoke must block visibility, or fire must spread or damage bodies, define an explicit deterministic gameplay representation and network/replay contract first; never infer gameplay from stochastic GPU density, particle coverage, or rendered brightness. This boundary still permits visual density/temperature later.

## Existing Rime seam, narrowly inspected

- [`engine/destruction/include/rime/destruction/events.hpp`](../../engine/destruction/include/rime/destruction/events.hpp) supplies immutable post-tick events with `world_bounds`, `magnitude`, kind, instance, and part/body IDs. `IslandDetached` can have zero magnitude, so a collapse smoke emission needs a positive baseline; intensity can then scale upward. The consumer owns fan-out; destruction has no VFX dependency.
- [`engine/vfx/include/rime/vfx/dust.hpp`](../../engine/vfx/include/rime/vfx/dust.hpp) has `ParticleField`, `EmitParams`, and `ImpactDust`, `LingeringSmoke`, `MuzzleFlash`. Its default CPU cap is 200; `emit_burst` silently drops overflow. Add attempted/spawned/dropped/retired counters at the consumer/field seam before increasing scale. Keep vfx depending only on core.
- [`engine/render/include/rime/render/fx_pass.hpp`](../../engine/render/include/rime/render/fx_pass.hpp) has an opt-in `FxSettings` gate, a 4096 draw cap with drop count, and a `GpuParticle` input. Its HDR additive pass suits glowing flashes, but smoke needs lit extinction/alpha and a transparency policy; additive billboards alone will read as glowing fog. Off must remain byte-identical, with no pass declared.
- [`engine/render/include/rime/render/scene_renderer.hpp`](../../engine/render/include/rime/render/scene_renderer.hpp) carries scene point lights and the existing shadow/SDF/DDGI destruction invalidation hooks. [`lighting/clustered.hpp`](../../engine/render/include/rime/render/lighting/clustered.hpp) accepts point-light rows via its existing cluster buffer. A fire-light bridge should append a bounded number of rows to scene extraction and count rejected rows. Do not make vfx own renderer objects.
- [`docs/adr/0042-fluids-track-reopened.md`](../../docs/adr/0042-fluids-track-reopened.md) already ratifies particle FX versus heightfield water, and queues `fx1b`, `fl1a`, `fx1c` strictly after M18. Its numerical budgets are estimates, and its recorded `frame` and `sim.block` p99 breaches make default-off seams, counter evidence, and paired A/B timings mandatory before scale-up.

## Milestones and gates

1. **General smoke / FX consumption (`fx1b.1` as first slice):** one effect emission description in a consumer-owned adapter, e.g. `FxEmission {family, world_bounds, baseline_count, intensity, seed, tick}`. Inputs may be scripted ambient plume, weapon event, or destruction event; a bounded queue forwards to `ParticleField`, then maps particles to `GpuParticle` for `FxParticlePass`. Keep the existing type boundaries: this is an adapter proposal, not a new shared fluid module. Turn on only in the demonstration consumer. Gate with visible on/off screenshot or pixel coverage delta, exact off-path frame comparison, attempted/spawned/dropped/retired/drawn reconciliation, and a scripted smoke source that exists independent of destruction. This establishes “general smoke” as a reusable visual capability.
2. **Destruction smoke (`fx1b.1` event slice):** consumer reads `World::events()` after each tick; map `PartDied` to impact dust, `IslandDetached` to a baseline `LingeringSmoke` plus magnitude scaling. Deduplicate by event kind/identity/tick if multiple presentation consumers might submit the same event; never use debris eviction as fresh smoke. Gate with a zero-impulse collapse producing visible smoke, smoke lifetime/coverage decay, budget drop telemetry, and an `enabled=false` negative control. Then consider `fx1b.2` GPU SoA simulation *only if* the measured 200-particle cap drops emissions during the collapse. A GPU path must preserve counters and the draw witness; benchmark the actual frame and GPU passes on the target hardware rather than inheriting ADR estimates.
3. **Fire lighting and smoke (`fx1c`):** consumer-owned `FxLightRequest {position, radius, linear_radiance, start_tick, duration_ticks, source_id}`; source is `WeaponFired` for one-frame flash or `IslandDetached`/explicit ignition for a 2–3-frame fireball. Cap concurrent requests (ADR suggests 8), deterministic priority on overflow, and append rows to the scene's existing point-light extraction; use one light curve to control *visual* `LingeringSmoke` emission. A persistent ignition state needs an authoritative gameplay owner if it affects damage; the visual bridge only reads it. Gate with flash radiance and DDGI irradiance deltas above measured noise versus no-light control, smoke-coverage curves for lit/unlit ignition, bounded light count, and paired frame timings. No new light pass is needed at this stage.
4. **Density volume / combustion, conditional later milestone:** only after billboards visibly fail a named camera/lighting/occlusion test and frame headroom exists. Prototype a small camera/local AABB density volume with emission → scalar/velocity advection → buoyancy → pressure projection → dissipation, then depth-aware ray marching with transmittance and lit scattering. Fuel/reaction/heat fields come only with a real propagation requirement. Require a CPU oracle or analytic mass/velocity tests, volume boundary tests, measured GPU memory and dispatch cost, temporal stability, and a full-frame A/B. Sparse allocation (Flow/NanoVDB) is a further option when bounded dense fields prove wasteful. This is distinct from the general particle smoke milestone and from `fl1a` water.

## Primary sources and code applicability

1. **Crane, Llamas, Tariq, [*Real-Time Simulation and Rendering of 3D Fluids*, GPU Gems 3 ch. 30](https://www.cs.cmu.edu/~kmcrane/Projects/GPUFluid/), [paper](https://www.cs.cmu.edu/~kmcrane/Projects/GPUFluid/paper.pdf) (2007).** Original professional 3D GPU solver and ray-march account, including smoke/fire, obstacles, and cost considerations. It is an algorithm/reference source, **not a code grant**. Its 64×64×128 performance figure is historical hardware context, not a Rime budget prediction.
2. **MantaFlow [buoyant smoke scene](https://github.com/tum-pbs/mantaflow/blob/master/scenes/plume_2d.py), [fire scene](https://github.com/tum-pbs/mantaflow/blob/master/scenes/fire.py), [LICENSE](https://github.com/tum-pbs/mantaflow/blob/master/LICENSE) (Apache-2.0).** Inspectable calls show density and velocity advection, outflow, buoyancy, and pressure projection; the fire scene adds fuel, reaction, heat, `processBurn`, and `updateFlame`. Best as a compact CPU oracle and sequencing reference. It is research software, not a drop-in renderer or Rime FX dependency. Direct reuse is legally possible under Apache-2.0 with notices, subject to root review.
3. **NVIDIA Flow 2 [advection shader](https://github.com/NVIDIA-Omniverse/PhysX/blob/main/flow/source/nvflow/shaders/AdvectionDensity1CS.hlsl), [pressure Jacobi shader](https://github.com/NVIDIA-Omniverse/PhysX/blob/main/flow/source/nvflow/shaders/PressureJacobiCS.hlsl), [pressure subtract shader](https://github.com/NVIDIA-Omniverse/PhysX/blob/main/flow/source/nvflow/shaders/PressureSubtractCS.hlsl), [Flow README](https://github.com/NVIDIA-Omniverse/PhysX/blob/main/flow/README.md).** Professional inspectable sparse-grid GPU implementation: virtual-to-real block mapping in the shader, advection and projection separate. The cited shader files each carry `SPDX-License-Identifier: BSD-3-Clause` and inline BSD conditions; **verify licenses file-by-file** before any direct reuse because this monorepo has other components/licenses. The older [Flow 1 repository](https://github.com/NVIDIAGameWorks/Flow) points to Flow 2; do not mistake its binary/demo packaging for the current shader source. Good architecture study, heavyweight for the first Rime smoke milestone.
4. **OpenVDB/NanoVDB [GPU/CPU data structure header](https://github.com/AcademySoftwareFoundation/openvdb/blob/master/nanovdb/nanovdb/NanoVDB.h), [FAQ](https://github.com/AcademySoftwareFoundation/openvdb/blob/master/doc/nanovdb/FAQ.md), [repository license](https://github.com/AcademySoftwareFoundation/openvdb/blob/master/LICENSE) (Apache-2.0).** Read-access, pointer-free sparse volume representation useful for later volume rendering or externally authored smoke. Its static topology/read-oriented design is **not an evolving smoke solver**; avoid presenting it as one. Direct code reuse is possible under Apache-2.0 with notices and root review, but integration cost is unjustified for bounded first fields.
5. **Wronski/Ubisoft, [*Volumetric Fog: Unified Compute Shader-Based Solution to Atmospheric Scattering*](https://bartwronski.com/wp-content/uploads/2014/08/bwronski_volumetric_fog_siggraph2014.pdf), [author publication page](https://bartwronski.com/publications/) (SIGGRAPH 2014).** Production rendering reference for varying-density smoke/fog, multiple lights, volumetric scattering and temporal integration in a froxel-like pipeline. It helps specify the *rendering* side of a later density milestone, independent of which solver generates density. Slides are not a source-code license; use ideas only. Rime's clustered-light froxels are a useful coordinate reference, not an already existing volume accumulation pass.
6. **Kim, Thürey, James, Gross, [*Wavelet Turbulence for Fluid Simulation*](https://www.cs.cornell.edu/~tedkim/wturb/) (2008).** Research source for procedural small-scale detail on top of coarse flow, as ADR-0042 mentions. Conceptual reference for `fx1b.2`; do not treat turbulence as a substitute for density advection/projection or copy code without a separate license check.

**Reuse rule:** above code is for inspection and comparison. No third-party source was copied into Rime. Any import requires a per-file license/notice review, dependency and platform fit, then local verification; article/paper ideas may be independently implemented without implying their text or sample code is licensed for copying.

uncommitted m17.8b brick (unchanged by this exercise). No engine logic touched, nothing committed.

## 1. The diagnostic

`samples/99-the-block/main.cpp:1584-1598`:

```cpp
bool scene_names_a_material = false;
session.client.world.query<render::MaterialAsset>().for_each(
    [&](ecs::Entity, render::MaterialAsset& a) {
        scene_names_a_material = scene_names_a_material || a.asset != 0;
    });
if (scene_names_a_material && !catalog) {
    // The scene ASKED for a cooked material and there is no manifest to answer with.
    // ...
    std::fprintf(stderr,
                 "99-the-block: the scene names a cooked material but no manifest was "
                 "found in %s — the street keeps the palette's flat look\n",
                 cooked.string().c_str());
}
```

**Exact gate:** `scene_names_a_material && !catalog`, evaluated in `Demo::start`
(`samples/99-the-block/main.cpp:1540`) right after `visuals->dress(...)`.

- `catalog` (`std::optional<assets::Manifest>`) is set a few lines earlier, only if
  `cooked/manifest.txt` exists and parses (`main.cpp:1548-1554`). No manifest at all → `catalog` is
  empty → this half of the AND is `true`.
- `scene_names_a_material` is `true` iff **any** entity in the loaded world carries a
  `render::MaterialAsset` component with `asset != 0` — i.e. an authored (or editor-saved) entity
  that names a cooked material id directly, the m17.8b entity-owned reference
  (`engine/render/include/rime/render/components.hpp:78-81`). A **generated** scene from
  `rime-blockgen` with no `--assets` never stamps this component (confirmed by reading
  `engine/app/block_gen_main.cpp`'s diff: `params.ground_material` stays `0` unless `--assets` is
  given, and `blockkit::assemble` only writes the `MaterialAsset` when it's nonzero — see
  `engine/blockkit/src/block.cpp`), so for such a scene this condition is always `false` and the
  warning is unreachable regardless of whether a manifest is present. This matches the background
  claim exactly: the path requires an *authored* naming of the material, not merely a missing cook.

The warning is a `fprintf(stderr, ...)` only — it does not abort, does not throw, and does not
gate anything else (the two checks that follow it, `textures_refused_unsupported()` and the
"nothing ended up wearing it" check, are independent and only run inside
`if (catalog && scene_names_a_material)`, which is false here, so they're skipped as designed).

## 2. Authoring a scene that names the cooked material

`rime-blockgen`'s binary in `build/release/bin` already carries the m17.8b `--assets` flag
(confirmed via `--help` and by diffing `engine/app/block_gen_main.cpp`), and `ninja -C build/release
the_block rime-blockgen` reported `ninja: no work to do` — **no rebuild was needed**, `build/release`
is current for both targets.

Found a cooked directory with a manifest already on disk from a prior test run:
`build/release/samples/99-the-block/cooked/manifest.txt`, listing (among others)
`ground:street#material0  material  d75cc3ed034b6f7b  street.rmat` — exactly the label
`blockkit::kGroundMaterialLabel` looks for.


`MaterialAsset::asset` on the ground entity — matching the diagnostic's precondition.

## 5. Findings

**Fired, verbatim:**
```
99-the-block: the scene names a cooked material but no manifest was found in /tmp/cooked_nomanifest — the street keeps the palette's flat look
```

**Behaviour otherwise:**
- No crash, no abort, exit status 0 both runs.
- No `VUID-*` validation output, no "refused" texture messages (`grep -inE
  "refus|panic|abort|segv|crash|VUID"` on the run B log returned nothing) — the code path this
  exercises is upstream of the BC-refusal checks (`bridge`/`GpuAssetBridge` are never constructed at
  all here, since they're gated on `catalog && scene_names_a_material`, which is false).
- Claims: run A (manifest present) holds **27/27**, including "render: the street wears its COOKED
  material". Run B (manifest absent) holds **26/26** — every claim except the COOKED-material one,
  which correctly does not appear at all (it isn't a `[fail]`, it's simply not evaluated, because
  the street fell back to the palette's flat look as the warning says). Every other claim — scale,
  player, weapon, breakage, net/replication, audio, the rest of render, lighting — is identical
  between the two runs and holds in both. No BC-refusal storm, no cascading failures: this is a
  single, isolated, correctly-scoped fallback.
- Same scene digest (`0xf25377b6995af14f`) in both runs, confirming the *only* variable between A
  and B is the presence of `manifest.txt` in the cooked dir, exactly as intended.

## VERDICT

**fix D FIRES as designed.**

The diagnostic at `samples/99-the-block/main.cpp:1595-1598`, gated on
`scene_names_a_material && !catalog`, is reachable only from a scene that authors a nonzero
`render::MaterialAsset` (an authored `.rscene` or an editor save) — not from a `rime-blockgen`
scene without `--assets`, matching the prior belief exactly. Once driven with an authored scene
(`rime-blockgen --assets <manifest> --out fixD.rscene`) against a cooked directory copy with
`manifest.txt` removed, the warning fires with the exact text shown above, the run completes
cleanly (exit 0, no crash), and every other claim that should still hold does hold (26/26, the one
material-specific claim correctly absent rather than failing). The real cooked directory's
`manifest.txt` was never touched — only a `cp -r` copy at `/tmp/cooked_nomanifest` had it removed.
